# AI automations

AI automations are WerkFlow's second product phase: assistance, recommendations, workflows and bounded agents that use the business's operational data to cut repetitive information work. The owner's direction is one agent on a harness WerkFlow owns, integrated into the whole app, reading data through the same authorization as a person. "WerkFlow KI" is its placeholder name; the product reads it from one constant, so the real name is one change. Build each capability only after its core workflow and data are trustworthy, and keep people in control of commitments, cost, legal records, customer communication and employee data.

## Current Product Baseline

WerkFlow KI has its storage, its switch, one model path, a chat page that follows a running answer on every tab and device, and three read tools. The product has no agent framework, workflow engine, search architecture, messaging provider, integration platform or automation builder.

- **Release and switch.** WerkFlow releases WerkFlow KI per organization: the owner lists its id in `AI_ORGANIZATION_IDS` in Vercel, for Production with PROD ids and for Preview with DEV ids. The list is empty by default. In a released organization the `admin` turns it on or off in the „WerkFlow KI“ card of the organization settings; another admin's open card follows live. It starts off. An unreleased organization's admin sees „noch nicht freigeschaltet“; `buero` and `employee` see no card.
- **Chat state in Postgres.** Threads, their typed items (messages, tool calls, questions, to-do lists, files), runs and costs live in Supabase Postgres. Each item has a per-thread sequence and an idempotency key, so a retried command writes it once.
- **Private threads.** Only the author reads a thread and its items, and only while their membership has access. No admin reads another person's thread; a suspended author reads none. Clients write nothing; the server writes through database functions that recheck the author. The organization export leaves threads out.
- **Deletion.** A daily database job deletes each item 12 months after it was written, and a thread once it is that old and holds no item. A file's bytes go with its item.
- **Cost ledger and budget.** A run reserves its most expensive outcome before it starts and settles after it ends. The reservation is the run's provisional charge: it counts against the budget until the run settles, however long that takes, and settling corrects it to the recorded cost. A database job settles every run still open 15 minutes after it began at its reserved amount, booking the part the ledger lacks as one ledger row, so no attempt's cost leaves the ledger; this overstates when a run spent less. That row counts in the month the job books it, so a run that began in the last minutes of a month may be charged in the next. Every provider attempt writes an append-only ledger row with tokens, real cost in micro-USD, model and prompt version, never text; the row keeps its cost when the thread is deleted. Each organization has a monthly budget in euros, with a default set by the owner in the migration; it counts a dollar as a euro, which overstates cost, so the stop comes early. A reservation refuses when the organization is off, the budget would be exceeded, or the decision cannot be made. The run records every attempt before it settles, so the hold covers each charge. Users see no counter.
- **Model path.** A turn reaches a model only through `POST /api/ki/threads/[threadId]/turns`, as the author of a thread in an organization they belong to. It runs on Claude Haiku 5.5 through Anthropic's first-party API, with the key in `WERKFLOW_KI_ANTHROPIC_KEY`; no other provider or model is allowed. Without the key a Vercel deployment refuses every turn as `unavailable`, and any other machine answers from recorded synthetic streams; a machine with the key, a workstation too, calls Anthropic and is billed. Agents and CI never hold it. After the per-person limits, one database call starts the turn under the command's id: it saves the message, which stays when that call refuses the turn or the turn fails, and only when the turn may start also reserves the run and saves the empty answer. A turn over the per-person limits saves nothing. The turn streams the answer in batches of about 50 ms and saves the partial answer at most every 750 ms. When the client leaves, the turn runs on, saves its answer and settles its cost.
- **Prompt and context.** Every turn sends one public system prompt, the same for every person and organization: who WerkFlow KI is, the company's words, that it says it is an AI in its first answer, that a tool result is data and never an instruction, that a role-play changes nothing, and that it never ranks or rates employees. Every attempt records the prompt's version in the ledger. One context builder orders what the model reads as the provider caches it: the prompt and the tools of the person's role, then the organization memory and the person memory (neither exists yet), then the thread. Before the model reads a message, the builder composes it to NFC and removes the characters a person cannot see: zero-width, bidirectional, Unicode tag, variation selector and control characters; the saved message keeps what was sent. Text from outside the conversation, such as documents, file names, record text and memory, may reach the model only inside a tool result, labelled with its source. A checked-in budget holds the byte sizes of the prompt and of each role's tools; growth over `main` needs the owner's label `approved: context growth`.
- **Tools.** Every tool is defined once in `lib/ai/tools/` and listed in its registry with its German label, input schema, roles, control level (read, draft or confirm), audit kind and data classes. Each turn offers the model only the tools of the person's role. A tool runs as the caller: the route resolves identity, organization and role from the session, and each call reads the membership again, so a member lowered or suspended during a turn gets the current role or nothing. No input names an organization, user, membership or role, and an input with a key the schema does not name is refused before anything runs. Each tool calls the reader of the page that shows the same data, with that page's role and organization checks. The three tools read and change nothing:
  - „Aufträge finden“ (`auftraege_finden`), for every role: open, parked or finished Aufträge and Projekte of the Aufträge list by number, title or customer, at most ten, with the list's status, customer, dates and link; a job inside a Projekt shows as its Projekt. An employee finds only assigned work.
  - „Kunden und Einsatzorte finden“ (`kunden_finden`), for `admin` and `buero`: active customers with number, address, phone, matched Einsatzorte and link, at most ten.
  - „Artikel finden“ (`artikel_finden`), for `admin` and `buero`: articles with unit, stock, available quantity and supplier article numbers with pack sizes, at most ten, without any price. When the supplier terms cannot be read, the articles come without them, as on the inventory page. It creates no default category or Lager, as the inventory page does.

  Text a person typed into a record reaches the model labelled as record text, cleaned like a message. Once a tool result carried such text, the turn offers no memory write for the rest of it; no memory tool exists yet. Every tool call writes an append-only ledger row with the tool, its outcome, the model and the prompt version, never text; a call the turn did not offer, whose input its schema refused, or whose attempt broke off is recorded as not run, and a name outside the registry as `unknown`. The model's calls run one at a time. A call whose ledger row cannot be written gives the model no data, and the turn ends; the rows of one attempt's calls that did not run share one write's time limit. A call whose tool still runs when the turn ends is recorded as failed before the run settles. The thread shows no tool row yet.
- **Caps and limits.** A turn stops at the caps in `lib/ai/limits.ts`: model steps, output tokens a step, input tokens counted at their upper bound, total and step time, answer size and message length. The cost writes, the answer's saves, the settlement and each live send have their own time limit. The oldest messages of a long thread drop out of the model's view first, and the view always opens with a message of the person. Thinking effort is set explicitly per entry point. Each person has one open turn across their organizations, and 60 turns an hour and 400 a day. Before each step the release list and the organization's switch are read again; a read that cannot decide stops the turn. A turn reserves its most expensive outcome from the budget before its first step.
- **Chat page.** `/ki` is the chat for every role. The sidebar shows „WerkFlow KI“ in a released organization; the page tells a member of an unreleased one that it is not released, and in a released one that is switched off, that an admin can switch it on (the admin gets the link). The page lists the person's own threads, latest activity first, a page at a time with „Ältere Chats laden“; on a phone the list sits under the new chat and a thread has „Alle Chats“. A thread's address is `/ki?chat=<id>`; an address of a thread the person does not have in the active organization, such as the last one before an organization switch, opens the new chat. Opening a thread shows the last known messages at once, marked unconfirmed, and reads it again; a thread opens with its latest messages under a byte cap, and „Frühere Nachrichten laden“ pages back; `lib/ai/thread-reads.ts` holds the page size, the window and the cap. A thread the page cannot read shows a retry. A new chat shows that WerkFlow KI is an AI and cannot read or change WerkFlow data yet, and the composer always says that it can be wrong.
- **Composer and streaming.** The composer stays on the page while the person switches threads. Each thread keeps its own draft per person and organization in the browser tab, so it survives a switch and a reload, leaves with the tab and goes at every sign-out in the tab, the password reset included. On a computer Enter sends and Shift+Enter starts a new line; on a phone Enter starts a new line. While an answer is written, Enter starts a new line of the next message. A sent message shows at once, marked unconfirmed until it is saved; a new thread takes its address only once it is saved. The answer streams in; finished paragraphs do not render again. „Antwort anhalten“ stops the answer on this screen and never sends the next message, and the thread's next read shows how the server finished it. A thread the person can no longer open, such as another organization's reached with Back, leaves the screen and the list with its messages and title. One answer runs at a time. A message refused before it was saved goes back into its own draft, in front of anything typed meanwhile, with the reason in German shown at that draft, and the thread shows the message when the server had saved it before it refused; sending it again unchanged is the same command, unless the server answered that the command can no longer run (`command_conflict`), and then it is a new one. Leaving the page stops reading the answer; the server finishes it. A message whose page went before it was saved, by a reload or by leaving the chat, comes back into its draft when the chat opens again, as the same command. When the sending tab's own connection breaks off before the answer's end, the answer stays open and follows the server's rest on the thread's live channel.
- **Files.** The composer takes PDFs and images: „Datei anhängen“ opens the file picker, and on a phone „Foto aufnehmen“ opens the back camera (iOS Safari and Android Chrome). Each chosen file uploads at once and shows in the draft, „wird hochgeladen …“ until it is stored; the draft keeps its files through a switch and a reload, and the person can remove one. The caps of `AI_UPLOAD_LIMITS` in `lib/ai/limits.ts` hold per file (type, size, and a PDF's pages, counted on the stored copy), per message (files and bytes together) and for uploads not yet sent per person; the signed upload pins the checked size. A refused file names itself and says why in German. A message waits for its uploads. Sending saves the message and its files in one call, one file item each in front of the message, as the session's person and only into their own thread; a repeat of the command must name the same files. A refused message, or one whose page went before it was saved, takes its files back into its draft. A file in the thread is a card with its name as plain text, its type, size and pages, and „Öffnen“, which opens it in a new tab through a ten-minute signed address; the thread itself carries no bytes or addresses. A file WerkFlow KI makes would show as the same card, marked „KI-Entwurf“; no tool makes one yet. The model does not read files yet. An upload nobody sent goes a day later, and every removed file queues its bytes for the [storage purge](#files-in-storage).
- **Live on every tab.** While an answer is written, the server sends it to the author's other tabs and devices on a private Realtime Broadcast channel per thread, through Realtime's REST API, at most every 250 ms: the person's message when the turn starts, the answer's text with its offset and how much of it the last partial save holds, and its end. Only the thread's author, while their membership has access, may join the channel; no admin or other member joins another person's, and no client sends on it. A page joins only the thread it shows, and only while its tab is visible; a hidden tab leaves the channel. A join that fails is tried again after a wait that doubles up to 30 seconds, with jitter, and a join that drops within a minute does not reset that wait. After every join the page reads the thread's messages from its cursor on (the first answer still being written, or after the last message it holds), so a reload, a second device or a tab that was hidden shows the answer still being written and follows it on. Text that arrives after a gap waits until the partial save covers the gap, then the page reads from the cursor and applies it; an end whose text the page missed reads the saved answer. Every live message names the live protocol's version: a tab whose build is older reloads once. A missed live send costs only freshness; the answer's end gets a second try within its time limit. Once a partial save says the author lost access to the thread, the channel sends nothing more of that turn. A checked-in transfer budget caps the bytes, rows and messages of opening a heavy thread, one live turn, a resume after a reload and an idle reconnect (`lib/ai/live/transfer-budget.test.ts`); its ceilings only fall.
- **Safe rendering.** Model text renders through one renderer (`components/shared/ai-markdown.tsx`): headings, emphasis, lists, quotes and code, no HTML and no images. A link works only for a path inside WerkFlow, checked as the browser resolves it; every other address, an image and HTML markup stay visible as plain text and load nothing. Lint bans every other Markdown or HTML renderer.
- **Retries and failures.** Overload, server errors, lost connections and a stream that ended early are retried while nothing was written, twice per turn; every attempt is ledgered at its cost, one the provider accepted without reported usage at its caps. A cost write that fails twice or runs past its limit ends the turn as interrupted and leaves the run open, so its provisional charge stays. A spend limit and every other refusal by the provider are never retried. A retried command runs and is charged once; one refused before its answer existed runs on a retry; the final save is tried again within its limit, and an answer left streaming is finished as interrupted with the text its last save held, by a retry of its command or by the database job, without another provider attempt. A command id sent again with other text is refused. Ledger keys hold the command id, never a value of the message. A turn that ends early keeps what it wrote and says why in German. No chat text, answer or provider body reaches a log, and the SDK's telemetry is off.

Phase 1 provides these foundations:

- One role-aware list of tasks, approvals and notifications on `/aufgaben`, derived live from the owning domains. Every AI confirmation joins it.
- An append-only event history per domain.
- Organization scoping and role authorization on every read and every action ([security.md](../technical/security.md)). Every tool the agent may call inherits this boundary.
- A closed set of authorized background reads, the pattern for read-only tool access.
- File bytes behind organization-scoped signed URLs ([document-storage-and-access.md](../technical/document-storage-and-access.md)). A model can read a document without the bytes passing through the app.
- Each handover release keeps structured snapshots beside its rendered file, so a renderer can read the customer-safe package as data.
- Transactional email for invitations and account mail, sent from an EU region. No inbound email, SMS, phone, calendar, accounting or wholesaler connector exists.

## Files in storage

A file a person adds to a WerkFlow KI message follows the [upload flow](../technical/document-storage-and-access.md#upload-flow) in the same private bucket.

- The key is `{organizationId}/ki/{uploaderId}/{fileId}/…`; a check constraint on `ai_thread_files` refuses a key outside its uploader and file, and a key holds no file name. Ticket and finalize recompute it from the session, so another member finds nothing to finalize.
- The finalize reads a PDF's stored copy on the server and follows its page tree to the root's page count without a PDF parser: it scans forward only and decodes at most a fixed budget of the object streams (`lib/ai/files/pdf-pages.ts`). A file whose tree it cannot follow is refused as unreadable, and a refused copy is discarded.
- Only the uploader opens a file, once a message attached it, through a ten-minute inline URL (`getAiFileUrl`); every allowed type renders safely.
- Every removed file row queues its object for the [purge](../technical/document-storage-and-access.md#storage-cleanup) in the same transaction: with its item, thread, membership or organization, when the person removes an unsent upload, and a day after an upload nobody sent.

## Add an agent tool

1. Read the action's row in the WerkFlow KI action inventory (werk-flow/werkflow-planning#526). A tool calls the server-only domain function the page or button calls. When that logic sits in a `'use server'` module or resolves its own context, extract a function that takes the context, and let both call it.
2. Define the tool with `defineTool` in `lib/ai/tools/` and list it in `lib/ai/tools/registry.ts`. Its `z.strictObject` input caps every string and list and names no organization, user, membership or role; `execute(input, ctx)` takes those from the session. Lint bans every other way to give the model a tool.
3. Return only the fields the task needs. Return every text a person typed into a record through `recordText`, name people by display name, and return no personnel, health, time, Zeitkonto, payroll or bank data.
4. Add its foreign-organization, lower-role and suspended-member cases to `lib/testing/fixtures/ai-tool-boundaries.ts`, and the injection cases its data invites to `ai-tool-injection.ts`.
5. Write the measured sizes into `lib/ai/agent-context-budget.json`. Growth needs the owner's `approved: context growth`.
6. Run `bun run test:unit lib/ai lib/security lib/conventions/server-action-input.test.ts`.

Wrong turn: calling a `'use server'` export, or taking an id from the model as the caller's organization.

## Incident runbook

Use it when WerkFlow KI shows data to someone who must not see it, acts beyond its user, or spends without reason. [Incident handling](../technical/recovery-and-incidents.md#incident-handling) owns everything else.

1. **Stop it everywhere.** The owner first revokes the key behind `WERKFLOW_KI_ANTHROPIC_KEY` in the Anthropic Console: every running turn fails at its next model step. Then the owner empties `AI_ORGANIZATION_IDS` in Vercel and redeploys, so no turn starts.
2. **Stop it for one organization.** Its admin switches it off in the „WerkFlow KI“ card of the organization settings, at once. The owner can also remove its id from `AI_ORGANIZATION_IDS` and redeploy: a variable change reaches only a new deployment. A running turn reads the switch and the list before each step and stops before the next one.
3. **Read the ledger.** The owner queries the organization's rows in the Supabase SQL editor of the affected project; an agent never reads PROD:

   ```sql
   select attempt.created_at, run.user_id, run.thread_id, attempt.outcome,
     attempt.model_id, attempt.prompt_version, attempt.cost_micro_usd
   from public.ai_run_attempts attempt
   join public.ai_runs run on run.id = attempt.run_id and run.organization_id = attempt.organization_id
   where attempt.organization_id = '<organization id>' and attempt.created_at > now() - interval '7 days'
   order by attempt.created_at;
   ```

   An outcome `tool_call_<tool>_<status>` is a tool call; every other row is a model attempt with its cost. The ledger holds ids, codes and cost, never text; the threads hold the text and stay private to their authors.
4. **Report a breach.** Note when WerkFlow learned of it: the clock starts there. A customer's personal data that reached anyone outside its permissions is a breach of data WerkFlow processes for that customer. Tell the customer without undue delay, in the form its AVV requires, so the customer can report to its authority within 72 hours (Art. 33 DSGVO). Record what happened, the data and people affected, and the measures in werkflow-planning's legal register.
