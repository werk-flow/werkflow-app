# Testing And Golden-Gate Harness

Status: living — last reviewed 2026-09-02

WerkFlow's regression safety net is a Playwright end-to-end harness that runs the roadmap's golden-gate scenarios (`GG-XX` in [gates.md](../plans/phase-1/gates.md)) as real multi-role browser journeys against a locally running app. Since 2026-08-28 (decision [0006](../decisions/0006-testing-architecture.md)) the Golden and audit batteries run against the **local Supabase stack** by default; a small **cloud canary suite** proves the live providers against dev Supabase and real R2 (see [environments.md](environments.md) for all three backends). The separate wave-audit battery is the exhaustive catalog-flow layer: golden gates stay lean, while audit coverage must account for every relevant stable flow ID in the [user-flow catalog](../product/user-flow-catalog.md). Wave 1 produced that coverage in wave-end sessions; since Wave 2 every slice ships its own audit spec at acceptance and the wave end only certifies (rule 12; [`wave-2-audit.md`](../plans/wave-2-audit.md)).

## Running

```bash
bun run env:local                           # route .env.local at the local stack (golden/audit)
bun run test:golden:focused --grep @P1-17  # iteration: one focused Golden tag
bun run test:audit:focused --grep @AUDIT-W2-P1-17  # iteration: one focused audit tag
bun run test:golden                         # certification: complete Golden battery (local stack)
bun run test:audit                          # certification: complete audit battery (local stack)
bun run env:dev                             # route .env.local at cloud DEV (canary)
bun run migrations:check                   # compare committed migrations with DEV before a cloud browser run
bun run test:canary                         # certification: the 9-test cloud canary suite
bun run test:canary:focused --grep "C3:"   # iteration: one canary test by title (the suite has no per-test tags)
bun run test:golden --target cloud          # wave-end/partner-milestone cloud battery only (D11)
bun run realtime:check                      # publication/replica-identity parity vs lib/realtime/tables.ts (also part of the local preflight)
bun run test:preflight                      # iteration preflight against the local target, without a run
bun run test:preflight:certification        # certification preflight; also checks the local target (append `cloud` for the canary target)
bun run test:runs list                      # run history with explicit open/cleaned retained-world state
bun run test:diagnostic --grep @P1-17-stage-boundaries --reuse-run <run-key>
bun run test:diagnostic:audit --grep @AUDIT-W2-P1-23 --reuse-run <run-key>
bun run test:runs classify <run-key> <product|harness|environment|transient> "<cause>" "<prevention>"
bun run test:runs cleanup <run-key>         # remove one retained disposable world
bunx playwright test --list                 # current Golden inventory (files and tests)
bunx playwright test --list --config playwright.audit.config.ts   # current audit inventory
```

Every run has an explicit **target**: golden and audit default to `local` (the WSL Supabase stack, [environments.md](environments.md)), the canary suite is pinned to `cloud` (dev Supabase + real R2). The preflight refuses a run whose `.env.local` routing does not match the requested target — a forgotten `env:local`/`env:dev` switch fails in seconds instead of sweeping the wrong backend. In local mode it health-checks the stack's REST endpoint, the bundled S3 storage endpoint, and the edge-function runtime (which `supabase db reset` leaves stopped) in three bounded attempts; in cloud mode it checks direct DEV Supabase and R2 endpoint reachability the same way. Retained-world cleanup verifies the same routing: cleaning a world recorded against a different backend is refused until you switch env. Iteration may use the development server. Certification requires a fresh production build and a verified workspace-owned server on `http://localhost:3000`; the preflight rejects a stale server, production routing, retained diagnostic worlds, and an unreachable authoritative backend. `bun run test:runs list` labels each retained world as `open` or `cleaned` and ends with the total number still open. Treat `Open retained worlds: 0` as the clean-inventory result; the historical run result can remain `failed_retained` after cleanup. The runner writes the complete console log, manifest, results, report, trace, screenshot, world identifiers, source fingerprint and build ID under `.agent-logs/playwright-runs/<run-key>/`. It prints only the start, final result and first failure to the interactive terminal. Launch long batteries unattended and react only to the final result or the first archived failure — never poll progress into the conversation (the P1-16 retrospective records progress polling as pure waste). All three configs stop after the first failure because later results in a serial shared world are not independent evidence. Record every gate run in [golden-gate-log.md](../plans/golden-gate-log.md). Never run plain `bun test` — unit tests run only via `bun run test:unit`, browser specs through the repository runner, and Playwright discovery via `bunx playwright test --list`. _Enforced (Tier 1): `bunfig.toml` scopes Bun's test root to `lib/`, so a bare `bun test` can no longer pick up browser specs._

### Run lanes and failure recovery

- **Iteration** is focused and requires `--grep`. Before creating a world, the runner discovers the requested and complete suite with Playwright `--list` and refuses a selection with zero tests or every test in the suite. A suite-wide tag such as `@CANARY` is certification, not focused proof.
- **Certification** runs a complete battery on frozen source, a fresh build and a fresh disposable world. It never reuses a failed world.
- **Diagnostic** requires both `--grep` and `--reuse-run <run-key>`. It keeps the failed run's organization, users and database state on the run's target backend (the local stack for battery runs, cloud DEV for canary runs), restores the role sessions, and reruns only the failing stage. This is the supported answer to a late failure: inspect and continue from the actual retained state instead of replaying 100 earlier tests or fabricating a lookalike state.
- Every failed browser run is archived and retained automatically. Classify it before another attempt. Two consecutive focused failures of the same class for the same suite, target and grep block another fresh-world iteration unless the operator supplies a concrete `--override-rerun-budget` reason. Cleanup is explicit after diagnosis. Certification refuses to start while any retained world is still live.
- A passed diagnostic proves the proposed explanation against the retained state. It is not acceptance evidence; the final certification still starts clean.
- **Direct** is the manifest label that `tests/golden/support/run-state.ts` records when Playwright starts outside `scripts/run-playwright.ts`. It is not a supported entry point. Use the runner scripts.

### The cloud canary suite

`tests/canary/canary.spec.ts` (`@CANARY`, nine tests, target well under 8 minutes) is the only battery that runs against the cloud per slice. It owns exactly the behavior the local stack cannot prove: real login and session refresh across protected navigations, a browser R2 upload with a signed-download byte round trip, cross-session Realtime delivery through cloud infrastructure (asserted against the D4 latency budget via `expectLiveWithin`), the invite flow with a real Resend mail, an organization-isolation smoke, clock-in/out with a persisted canonical session and segment, a server-action write with persisted read-back, the HaveIBeenPwned leaked-password rejection copy (HIBP needs internet — canary-only by nature), and DEV-migration-history parity with the committed files. Cloud preflight now checks that parity before browser setup or world creation; C9 repeats the assertion inside the accepted battery so drift during a run still fails certification. `bun run migrations:check` exposes the same read-only check for diagnosis.

**Growth rule (owner requirement, decision D10):** the canary is open to additions by future agents, but must stay short. Add a test only for behavior that can only be proven in the cloud or is distinctly more valuable proven there; anything provable locally belongs in the Golden or audit battery. Every canary addition or removal is recorded in the [platform-hardening ledger](../plans/platform-hardening.md) with its reason.

Slice acceptance since decision [0006](../decisions/0006-testing-architecture.md): full Golden and audit certification against the **local** stack, plus a green canary run against the cloud. The full battery runs against the cloud only at wave-end certification gates and before owner-named partner milestones (D11).

Hard-earned operational rules (2026-08-04):

1. **Run gates against a production build**: `bun run build`, then `bun start`, then the gate. `next dev` compiles routes on demand mid-test and produces flaky timeouts; the dev server is for iterating on a slice, the production build is for the gate that counts.
2. **Port 3000 only.** Direct-to-R2 uploads are CORS-authorized for `http://localhost:3000`; a server on any other port makes browser uploads fail with misleading symptoms.
3. **Never run `bun run build` while a server is serving `.next`.** The rebuild deletes the running server's chunk files; pages then load without JavaScript (broken hydration, forms fall back to native submits). Stop the server, build, start again.
4. **Retain failures, clean deliberately.** Failed worlds are retained automatically and registered by run key. Use diagnostic reuse, then `bun run test:runs cleanup <run-key>`. `KEEP_WORLD=1` is only an exceptional manual override; certification will not run until retained worlds are resolved.
5. Browser installation (`bunx playwright install chromium`) is a per-machine step that belongs with the onboarding checklist in [environments.md](environments.md#per-machine-onboarding-checklist), not in this doc.
6. `GOLDEN_BASE_URL` can point the run at another server, but direct-to-R2 uploads will fail on any origin the bucket CORS does not allow — stick to port 3000 unless the CORS policy was deliberately extended.
7. **The production server must outlive the entire suite.** Start `bun start` as a detached/background process with no tool time limit and health-check `http://localhost:3000` before starting Playwright. A foreground server under a tool timeout dies mid-suite and invalidates the whole run (`ERR_CONNECTION_REFUSED` on every remaining test — this happened in the P1-05 cycle).
8. **Separate iteration from certification.** Order per slice: implement → self-review and every intended quality/review pass → review fixes → statics and units → fresh production build/server → focused iteration proof → required certification batteries. Do not start a complete battery to discover ordinary defects. The runner's changed-file impact registry requires a current-fingerprint focused proof before certification where a known shared surface has a narrower owning scope; its first mapping makes changes to `components/auftraege/field-work-pack-page.tsx` prove `@P1-16` before a complete Golden run. Extend that registry when an incident establishes another stable mapping. Any later application or Golden-code change invalidates its build and certification evidence; an audit-only fix reopens only the scoped audit evidence allowed by the phase protocol. Post-freeze application fixes batch into one delta-scoped review pass per the CodeRabbit protocol ([coderabbit.md](coderabbit.md#post-freeze-review-fixes-are-batched)); only an authorization or data-integrity fix reopens review immediately.
9. **After any fix, prove the affected scope first.** The runner requires `--grep` in iteration, verifies that the grep selects fewer than the complete suite and records a source fingerprint. A full-run retry is blocked until the failed run is classified and a later focused run covering the failed spec passes on the current source. Known serial dependencies are also checked from discovered test titles before a fresh iteration world exists: the learned A1-02/A1-03 selection is rejected unless its A1-01/A1-07 producer chain is included. A retained-world diagnostic may select only the failing stage because its producer state already exists. New slice specs ship stage-split at persisted boundaries (see Conventions) so a late failure can be diagnosed without replaying its setup.
10. **A failed full run is never confirmation, and full reruns have a budget.** The first retry requires classification plus a focused proof covering the failed spec; interrupted and timed-out full runs count as consumed attempts. If two consecutive full attempts fail in the same class, the runner blocks a third unless the operator supplies a concrete `--override-rerun-budget` reason after investigation. Never blind-retry. The durable incident entry records the run key, class, evidence, cause, fix and prevention.
11. **Never trust an existing port-3000 server after a rebuild.** After `bun run build`, stop the verified workspace listener, start the new build in a fresh detached process, and health-check it. Certification preflight compares the listener start time with `.next/BUILD_ID`, checks its command line and refuses an unverified listener.
12. **Audit catalog coverage is exhaustive and many-to-many.** Every user-flow bullet relevant to an audit session has one stable catalog flow ID, and every relevant ID must appear in at least one ledger row. A ledger row or Playwright test may cover multiple catalog IDs, and a catalog ID may span multiple rows/tests; test count never needs to equal flow count. Mapping an ID means the actual assertion bodies evidence every observable clause of that catalog bullet, including roles, defaults, warnings, denials, state transitions, persistence, privacy, and negative promises. A title, helper call, implementation path, or partial assertion is not full coverage. Record partial mappings as `partial`, name the missing clauses, and supplement them before closure. Manual evidence may replace Playwright only when automation genuinely cannot observe the behavior and the owner explicitly approves that named exception. Session closure requires set equality between the catalog IDs owned by the session and the union mapped in its ledger rows, every mapped bullet fully evidenced, and zero partial or unmapped IDs. A material catalog-wording change reopens that ID until its mapped assertion bodies are rechecked. **Since Wave 2, this rule applies per slice, not per wave-end session:** every slice ships its own audit spec in `tests/audit/wave-N/` mapping all of its catalog flow IDs, with ledger rows closed in the wave's audit doc as part of slice acceptance (see [wave-2-audit.md](../plans/wave-2-audit.md) and [protocol.md](../plans/phase-1/protocol.md)). The wave-end audit shrinks to a certification gate: catalog-vs-ledger set equality, one full Golden run plus the full wave battery on one build, and nothing else. Wave 1's retroactive R1 reconciliation is the recorded cost of doing it the other way.
13. **Assert persisted state, never the optimistic echo.** After any mutation, the success assertion must read state the server actually committed: a fresh navigation, a second session/role, the read-only `db.ts` helpers, or a UI element that only renders from refetched data. Snapshot the relevant identity/count/version before the action and wait for that exact fact to change; polling only for a nonzero count or an already-existing row can accept the predecessor state before the server action settles. Navigate explicitly to the persisted route before testing its detail view. The instant visual echo of an optimistic update can be green while the server write failed or never committed — a Wave 1 audit test asserted a checklist item the admin's optimistic state showed, the insert had not committed, and the employee's session correctly saw nothing while the test passed. Where an optimistic marker exists (pending style, spinner), wait for it to CLEAR before asserting. This generalizes the older "assert resulting state, not flashes" gotcha into a hard rule.
14. **Serialize local infrastructure gates.** Do not run `supabase db reset`, a WSL-backed SQL assertion command, and `bun run test:unit` concurrently on Windows. The SQL runner and reset share the WSL/Docker service boundary, while the unit suite intentionally spawns child Bun processes for its file-lock proof; parallel tool orchestration can yield `E_ACCESSDENIED`/`EPERM` without exercising product code. Run reset, SQL assertions and units as separate commands and classify a sandbox child-spawn denial as environment. This remains Tier 3 because repository code cannot statically control whether an external agent launches independent shell commands in parallel.
15. **Never run two Playwright batteries concurrently.** The Golden, audit, and canary configs share `tests/golden/.artifacts` (`world.json` and the role auth states), and each global setup removes leftover worlds. A concurrent run destroys the other run's world. Run batteries one after another. This is Tier 3 for the same reason as rule 14.

Playwright writes three artifacts per failure into `tests/golden/.results/<test>/`:

1. **`error-context.md` — read this first.** It contains the failing assertion plus a YAML accessibility snapshot of the page at failure time. Most fixes come straight from seeing what roles/names the page actually exposes (e.g. the employee picker is a `combobox`, its options are `button`s inside a `listbox`, dialogs sometimes close without a success flash).
2. `test-failed-1.png` — screenshot.
3. `trace.zip` — full replay (`bunx playwright show-trace <path>`), rarely needed.

Known interaction gotchas are documented as comments in `tests/golden/support/steps.ts` — read them before writing new steps. The recurring classes so far: duplicate desktop/mobile text nodes (use `visibleText` for a positive assertion and `textInDom` for absence), Escape closing the whole dialog instead of an inner popover (dismiss by clicking elsewhere), success flashes that do or don't exist per dialog (assert resulting state, not flashes), upload dialogs whose "abgeschlossen" counter includes failed files (also assert the absence of error text), and a pre-hydration login race (the setup retries; the form itself is hardened with `method="post"`).

Before rerunning anything, classify the failure: **product defect** (fix the app; for a non-trivial defect, follow the `diagnosing-bugs` skill's feedback-loop discipline), **harness defect** (fix the step/locator, then focused spec first), **environment** (server died, browser missing, sandbox — fix the environment, the run proves nothing about code), or **known transient** (the documented Resend timeout and Realtime-freshness intermittents — rerun before debugging code you didn't change). Two failures of the same class in a row mean stop and investigate instead of trying variations.

The **refresh-interrupted dialog** class deserves its own note because it is a product pattern, not test flakiness: the app's Realtime subscriptions trigger refreshes, and a refresh landing while a dialog is open can remount or reset it mid-interaction (lost typed input, a reopened form snapping back, a "second Uhrzeit locator replaced under the click"). Since the Stage B consolidation every live surface consumes Realtime through the live-view primitive, whose dialog suspension plus one queued catch-up is exactly the fix for this class ([realtime-and-caching.md](realtime-and-caching.md)). A mid-dialog reset therefore points at a surface that bypasses the primitive (lint should already have caught it) — treat it as a candidate product defect, not a locator problem.

A class documented 2026-08-21: **stalled server-action POST**. Signature: a dialog frozen on its pending state („Wird gelöscht...", a disabled „Speichern") for 60s+ while the URL never changes — the browser's server-action request (or its response) hung, even though the underlying database write often committed (verify via the Supabase edge logs: the REST call may show 2xx at the stall time). This is neither a locator problem nor, usually, app logic: during the M2 consolidation session it hit customer deletion, assignment saves, and even harness logins on the same day the dev project migrated compute. Since then the server-side Supabase clients carry a 30 s fetch timeout (`lib/supabase/fetch-with-timeout.ts`), so a stalled request rejects and surfaces through normal error handling instead of hanging forever; post-delete redirects additionally hard-navigate. If this signature reappears, treat it as environment first (dev-project health, network), and check the edge logs before touching app code.

A further environment class documented 2026-08-09 (numbers from that era's 90 s budget and smaller suite; the class itself survives any budget): **long-run latency**. Under heavy machine or file-sync load, per-test times balloon suite-wide and dialog interactions of _old, long-green_ tests can exhaust even today's 180 s budget (element mounted but "not visible" for over a minute while paint stalls). Signature: different tests fail across attempts, per-test times balloon suite-wide, and the focused spec passes at normal speed. Classify with a focused run; do not "fix" green tests — rerun in a quieter environment.

A test that passes must mean the business outcome happened: pair every positive assertion with the state it produced (row exists, URL changed, count is zero for the other role) rather than trusting transient UI feedback.

## Conventions

- One spec file per slice, tests in `serial` mode. The gate tag `@GG-XX` sits on the spec of the slice that owns the gate; `GG-07` spans `p1-23.spec.ts` and `p1-24.spec.ts`.
- **Every new Golden slice spec ships stage-split — one monolithic slice test is a review flag.** Follow the P1-16 model: separate serial tests at persisted stage boundaries with stable per-stage grep tags (`@P1-XX-stage-setup`, `-execution`, `-boundaries`, or slice-appropriate names). Each later stage verifies its persisted precondition through a read-only database helper or a reloaded UI fact, never module-local memory, so a diagnostic run can resume exactly the failed stage on a retained world without replaying its predecessors. Stage boundaries also keep cheap checks (role denial, privacy) from hiding behind expensive ones (uploads, material movements).
- Wave-audit specs follow [wave-1-audit.md](../plans/wave-1-audit.md) and [wave-2-audit.md](../plans/wave-2-audit.md). Each session ledger records stable catalog flow IDs and concise whole-bullet clause evidence per rule 12; do not infer completeness from test counts or titles.
- The cross-wave layout audit `tests/audit/layout/mobile-viewport.spec.ts` (`@AUDIT-LAYOUT`, added 2026-09-03 by the [UI/UX hardening](../plans/uiux-hardening-2026-09.md)) walks every authenticated area at 375 px as admin and employee and fails on page-level horizontal scroll, document-level vertical scroll, or a rendered native select or date-like input. It runs inside the audit battery and focused via `bun run test:audit:focused --grep @AUDIT-LAYOUT`; add a route to its list when a new area ships.
- New slices extend `steps.ts` with their business actions and add/extend the gate spec named by their slice index row in [roadmap.md](../plans/phase-1/roadmap.md). Do not put raw selectors in specs.
- Use `visibleText()` only for positive text assertions. Pages often render the same text twice in a desktop table and a hidden mobile card, so the helper selects a visible instance.
- Use `textInDom()` for zero-count text assertions. Privacy and role-boundary checks must inspect every matching DOM node, including hidden responsive renders. ESLint rejects `visibleText(...).toHaveCount(0)`.
- Scope spec locators by a semantic row, section, dialog, or role. ESLint rejects raw CSS selectors rooted at a Playwright `Page`, including aliases and pages returned by popup helpers. It also rejects `.first()`, `.last()`, `.nth()`, fixed sleeps, per-test timeout overrides, skipped or focused tests, and hard-coded cleanup markers in spec files. Put a bounded exception in a named support helper and document why the semantic API cannot express it.
- Two ESLint rules in `eslint.config.mjs` guard the harness itself. `signOut()` with no arguments is rejected in every `.ts` and `.tsx` file (`authSelectors`), because the default scope is `global` and revokes the user's sessions on every device; pass `{ scope: 'local' }`. The production Supabase project ref is rejected anywhere under `tests/**` (`prodRefSelectors`), so the harness can only reach the dev project or the local stack.
- Absence assertions (`toHaveCount(0)`) prove role/organization boundaries; every gate should include at least one negative check. The unit convention test checks only the structural presence of a negative form. Review still verifies that the assertion proves the intended boundary or absence of side effects.
- Success signals differ per dialog: some show a flash (`Kunde erfolgreich erstellt!`), some close immediately — assert the resulting row/state, not only flashes.
- Seeded identities use `@werkflow-golden.test` emails and org names prefixed `Golden Test SHK` / `Fremde Firma`; the invite scenario additionally uses Resend's bounce-safe test address pattern `delivered+gg-<runId>@resend.dev` so the real invite email sends without harming sender reputation. The leftover cleaner keys on exactly these markers. Never use these markers for real data.
- `tests/golden/support/db.ts` holds read-only service-role lookups for assertions the UI cannot prove (the invite code inside the email link, stock-ledger consistency). Specs still drive every user-visible action through the UI.
- **Specs inherit state from every earlier spec** (serial, alphabetical, one shared world): members joined in `@P1-03`, schedules and the holiday calendar from `@P1-04`, and so on. A step that passes in a focused run can legitimately fail only in the full run because names appear in more places or extra action buttons exist — that is the full run doing its job. Scope locators semantically (the exact section/row, `exact: true` names), never by count or position. State `@P1-06` leaves behind: `leave_approval` ends in `selected` mode with the admin as sole holder (Büro and the invited Büro member lost it), the employee has an extra Vollzeit condition valid from the run day + 1 carrying 30 vacation days, the employee keeps one approved future half-day vacation and one rejected request, and Büro keeps one approved future single-day vacation.
- **`GG-02` placement and dual-mode design (P1-07):** the gate spec lives in `p1-07.spec.ts` so it sorts AFTER every slice spec — it inherits the full suite-end state instead of injecting business facts that six earlier specs would silently inherit (the rejected alternative was seeding dedicated fixtures and running the gate early). Because the validation ladder also runs it focused on a fresh world, the spec is deliberately dual-mode: its first test pins the responsibility state itself (`time_approval` → employee sole, `leave_approval` → admin sole — a recorded no-op re-selection in the full run), it creates and closes its own client request instead of relying on GG-01's leftover, and every count expectation (inherited notifications, unified badge numbers) is derived from the database at runtime rather than hardcoded per mode. State `@GG-02` leaves behind (nothing runs after it, but seeder/`KEEP_WORLD` debugging should know): two extra no-op responsibility configurations, one closed GG02 client request, new schedule versions valid from run-day+1 for the employee (Mo–Fr 6h) and Büro (Mo–Fr 8h), one approved Büro manual time entry from yesterday 10–11, and for the employee one extra withdrawn, one cancelled, and one rejected vacation request plus attention read markers/events.

### Live-provider limits after the deterministic/canary split

Decision [0006](../decisions/0006-testing-architecture.md) resolved the old structural limit: the long serial batteries no longer depend on live cloud providers, so a network hiccup can no longer fail an application certification. What remains true:

- A **cloud-target** run (canary, wave-end battery) still carries the provider dependency. Preflight cannot guarantee a later network window; classify environment failures honestly and never retry availability luck into evidence.
- The local stack is deterministic infrastructure, not magic: WSL, Docker, and machine load still produce environment-class failures (the WSL address changes on restart, `db reset` stops the edge runtime, heavy load still stretches budgets). The preflight catches the known ones with named remedies; classify anything new before rerunning.
- One green run still proves one ordering. The full battery remains a certification signal, not an iteration loop.

The Golden config uses a 180 s per-test budget for local runs, the audit config 240 s, and both use 300 s for cloud-target runs. The canary always uses 300 s. Spec files have no per-test overrides: ESLint rejects `test.setTimeout()` and `test.slow()`. Realtime-sensitive mutation helpers may retry one complete transaction only when a refresh demonstrably removed the UI before submission; after submission they must reassert persisted state rather than repeat the mutation. A missing live refresh may use one reload only where the authoritative persisted row is still asserted. These guards keep the business assertions strict without turning delivery latency into duplicate writes.
