# Testing And Golden-Gate Harness

Status: living — last reviewed 2026-08-25

WerkFlow's regression safety net is a Playwright end-to-end harness that runs the roadmap's golden-gate scenarios (`GG-XX` in [`docs/plans/phase-1/gates.md`](../plans/phase-1/gates.md)) as real multi-role browser journeys against a locally running app and the dedicated dev Supabase project (see [environments.md](environments.md)). The separate wave-audit battery is the exhaustive catalog-flow layer: golden gates stay lean, while audit coverage must account for every relevant stable flow ID in [`docs/product/user-flow-catalog.md`](../product/user-flow-catalog.md). Wave 1 produced that coverage in wave-end sessions; since Wave 2 every slice ships its own audit spec at acceptance and the wave end only certifies (rule 12; [`wave-2-audit.md`](../plans/wave-2-audit.md)).

## Running

```bash
bun run test:golden:focused --grep @P1-16  # iteration: one focused Golden tag
bun run test:audit:focused --grep @AUDIT-W2-P1-16  # iteration: one focused audit tag
bun run test:golden                         # certification: complete Golden battery
bun run test:audit                          # certification: complete audit battery
bun run test:runs list                      # archived run and retained-world inventory
bun run test:diagnostic --grep @P1-16-stage-boundaries --reuse-run <run-key>
bun run test:runs classify <run-key> <product|harness|environment|transient> "<cause>" "<prevention>"
bun run test:runs cleanup <run-key>         # remove one retained disposable world
```

Requirements: `.env.local` must route to DEV Supabase and `werkflow-documents-dev`. Every lane checks direct DEV Supabase and R2 endpoint reachability in three bounded attempts before launching a browser. Iteration may use the development server. Certification requires a fresh production build and a verified workspace-owned server on `http://localhost:3000`; the preflight rejects a stale server, production routing, retained diagnostic worlds, and an unreachable authoritative backend. The runner writes the complete console log, manifest, results, report, trace, screenshot, world identifiers, source fingerprint and build ID under `.agent-logs/playwright-runs/<run-key>/`. It prints only the start, final result and first failure to the interactive terminal. Both configs stop after the first failure because later results in a serial shared world are not independent evidence. Record every gate run in [`docs/plans/golden-gate-log.md`](../plans/golden-gate-log.md). Never run plain `bun test` — unit tests run only via `bun run test:unit`, browser specs through the repository runner, and Playwright discovery via `bunx playwright test --list`.

### Run lanes and failure recovery

- **Iteration** is focused and requires `--grep`. It is the only lane for normal selector, product and harness development.
- **Certification** runs a complete battery on frozen source, a fresh build and a fresh disposable world. It never reuses a failed world.
- **Diagnostic** requires both `--grep` and `--reuse-run <run-key>`. It keeps the failed run's live DEV organization, users and database state, restores the role sessions, and reruns only the failing stage. This is the supported answer to a late failure: inspect and continue from the actual retained state instead of replaying 100 earlier tests or fabricating a lookalike state.
- Every failed browser run is archived and retained automatically. Classify it before another full certification. Cleanup is explicit after diagnosis. Certification refuses to start while any retained world is still live.
- A passed diagnostic proves the proposed explanation against the retained state. It is not acceptance evidence; the final certification still starts clean.

Hard-earned operational rules (2026-08-04):

1. **Run gates against a production build**: `bun run build`, then `bun start`, then the gate. `next dev` compiles routes on demand mid-test and produces flaky timeouts; the dev server is for iterating on a slice, the production build is for the gate that counts.
2. **Port 3000 only.** Direct-to-R2 uploads are CORS-authorized for `http://localhost:3000`; a server on any other port makes browser uploads fail with misleading symptoms.
3. **Never run `bun run build` while a server is serving `.next`.** The rebuild deletes the running server's chunk files; pages then load without JavaScript (broken hydration, forms fall back to native submits). Stop the server, build, start again.
4. **Retain failures, clean deliberately.** Failed worlds are retained automatically and registered by run key. Use diagnostic reuse, then `bun run test:runs cleanup <run-key>`. `KEEP_WORLD=1` is only an exceptional manual override; certification will not run until retained worlds are resolved.
5. Chromium is already installed (`bunx playwright install chromium` has been run on this machine); do not reinstall unless `playwright test` itself reports a missing browser.
6. `GOLDEN_BASE_URL` can point the run at another server, but direct-to-R2 uploads will fail on any origin the bucket CORS does not allow — stick to port 3000 unless the CORS policy was deliberately extended.
7. **The production server must outlive the entire suite.** Start `bun start` as a detached/background process with no tool time limit and health-check `http://localhost:3000` before starting Playwright. A foreground server under a tool timeout dies mid-suite and invalidates the whole run (`ERR_CONNECTION_REFUSED` on every remaining test — this happened in the P1-05 cycle).
8. **Separate iteration from certification.** Order per slice: implement → self-review and every intended quality/review pass → review fixes → statics and units → fresh production build/server → focused iteration proof → required certification batteries. Do not start a complete battery to discover ordinary defects. Any later application or Golden-code change invalidates its build and certification evidence; an audit-only fix reopens only the scoped audit evidence allowed by the phase protocol.
9. **After any fix, prove the affected scope first.** The runner requires `--grep` in iteration and records a source fingerprint. A full-run retry is blocked until the failed run is classified and a later focused run passes on the current source. Long specs must expose stable, persisted stage tags so a late failure can be diagnosed without replaying their setup.
10. **A failed full run is never confirmation, and full reruns have a budget.** The first retry requires classification plus focused proof. If two consecutive full attempts fail in the same class, the runner blocks a third unless the operator supplies a concrete `--override-rerun-budget` reason after investigation. Never blind-retry. The durable incident entry records the run key, class, evidence, cause, fix and prevention.
11. **Never trust an existing port-3000 server after a rebuild.** After `bun run build`, stop the verified workspace listener, start the new build in a fresh detached process, and health-check it. Certification preflight compares the listener start time with `.next/BUILD_ID`, checks its command line and refuses an unverified listener.
12. **Audit catalog coverage is exhaustive and many-to-many.** Every user-flow bullet relevant to an audit session has one stable catalog flow ID, and every relevant ID must appear in at least one ledger row. A ledger row or Playwright test may cover multiple catalog IDs, and a catalog ID may span multiple rows/tests; test count never needs to equal flow count. Mapping an ID means the actual assertion bodies evidence every observable clause of that catalog bullet, including roles, defaults, warnings, denials, state transitions, persistence, privacy, and negative promises. A title, helper call, implementation path, or partial assertion is not full coverage. Record partial mappings as `partial`, name the missing clauses, and supplement them before closure. Manual evidence may replace Playwright only when automation genuinely cannot observe the behavior and the owner explicitly approves that named exception. Session closure requires set equality between the catalog IDs owned by the session and the union mapped in its ledger rows, every mapped bullet fully evidenced, and zero partial or unmapped IDs. A material catalog-wording change reopens that ID until its mapped assertion bodies are rechecked. **Since Wave 2, this rule applies per slice, not per wave-end session:** every slice ships its own audit spec in `tests/audit/wave-N/` mapping all of its catalog flow IDs, with ledger rows closed in the wave's audit doc as part of slice acceptance (see `docs/plans/wave-2-audit.md` and `docs/plans/phase-1/protocol.md`). The wave-end audit shrinks to a certification gate: catalog-vs-ledger set equality, one full Golden run plus the full wave battery on one build, and nothing else. Wave 1's retroactive R1 reconciliation is the recorded cost of doing it the other way.
13. **Assert persisted state, never the optimistic echo.** After any mutation, the success assertion must read state the server actually committed: a fresh navigation, a second session/role, the read-only `db.ts` helpers, or a UI element that only renders from refetched data. The instant visual echo of an optimistic update can be green while the server write failed or never committed — a Wave 1 audit test asserted a checklist item the admin's optimistic state showed, the insert had not committed, and the employee's session correctly saw nothing while the test passed. Where an optimistic marker exists (pending style, spinner), wait for it to CLEAR before asserting. This generalizes the older "assert resulting state, not flashes" gotcha into a hard rule.

Playwright writes three artifacts per failure into `tests/golden/.results/<test>/`:

1. **`error-context.md` — read this first.** It contains the failing assertion plus a YAML accessibility snapshot of the page at failure time. Most fixes come straight from seeing what roles/names the page actually exposes (e.g. the employee picker is a `combobox`, its options are `button`s inside a `listbox`, dialogs sometimes close without a success flash).
2. `test-failed-1.png` — screenshot.
3. `trace.zip` — full replay (`bunx playwright show-trace <path>`), rarely needed.

Known interaction gotchas are documented as comments in `tests/golden/support/steps.ts` — read them before writing new steps. The recurring classes so far: duplicate desktop/mobile text nodes (use `visibleText`), Escape closing the whole dialog instead of an inner popover (dismiss by clicking elsewhere), success flashes that do or don't exist per dialog (assert resulting state, not flashes), upload dialogs whose "abgeschlossen" counter includes failed files (also assert the absence of error text), and a pre-hydration login race (the setup retries; the form itself is hardened with `method="post"`).

Before rerunning anything, classify the failure: **product defect** (fix the app), **harness defect** (fix the step/locator, then focused spec first), **environment** (server died, browser missing, sandbox — fix the environment, the run proves nothing about code), or **known transient** (the documented Resend timeout and Realtime-freshness intermittents — rerun before debugging code you didn't change). Two failures of the same class in a row mean stop and investigate instead of trying variations.

The **refresh-interrupted dialog** class deserves its own note because it is a product pattern, not test flakiness: the app's Realtime subscriptions call `router.refresh()`, and a refresh landing while a dialog is open can remount or reset it mid-interaction (lost typed input, a reopened form snapping back, a "second Uhrzeit locator replaced under the click"). Several Wave 1 audit fixes patched individual dialogs with suspend-refresh guards (`useRealtimeRouterRefresh`'s suspend + pending-timer drop). Until the UI/UX consolidation standardizes that mechanism across every dialog (its brief owns this — `docs/plans/uiux-consolidation.md`), treat a mid-dialog reset in an UNPATCHED dialog as a candidate product defect of this class, not as a locator problem: check whether the dialog suspends Realtime before hardening the test.

A class documented 2026-08-21: **stalled server-action POST**. Signature: a dialog frozen on its pending state („Wird gelöscht...", a disabled „Speichern") for 60s+ while the URL never changes — the browser's server-action request (or its response) hung, even though the underlying database write often committed (verify via the Supabase edge logs: the REST call may show 2xx at the stall time). This is neither a locator problem nor, usually, app logic: during the M2 consolidation session it hit customer deletion, assignment saves, and even harness logins on the same day the dev project migrated compute. Since then the server-side Supabase clients carry a 30 s fetch timeout (`lib/supabase/fetch-with-timeout.ts`), so a stalled request rejects and surfaces through normal error handling instead of hanging forever; post-delete redirects additionally hard-navigate. If this signature reappears, treat it as environment first (dev-project health, network), and check the edge logs before touching app code.

A further environment class documented 2026-08-09: **long-run latency**. Under heavy machine or file-sync load the full suite stretches to 15–17 minutes and the 90s per-test budget can trip dialog interactions of *old, long-green* tests (element mounted but "not visible" for over a minute while paint stalls). Signature: different tests fail across attempts, per-test times balloon suite-wide, and the focused spec passes at normal speed. Classify with a focused run; do not "fix" green tests — rerun in a quieter environment.

A test that passes must mean the business outcome happened: pair every positive assertion with the state it produced (row exists, URL changed, count is zero for the other role) rather than trusting transient UI feedback.

## Conventions

- One spec file per golden gate, tagged `@GG-XX`, tests in `serial` mode.
- Wave-audit specs follow `docs/plans/wave-1-audit.md`. Each session ledger records stable catalog flow IDs and concise whole-bullet clause evidence per rule 12; do not infer completeness from test counts or titles.
- New slices extend `steps.ts` with their business actions and add/extend the gate spec named by their slice index row in `docs/plans/phase-1/roadmap.md`. Do not put raw selectors in specs.
- Use `visibleText()` for text assertions — pages render text twice (desktop table + hidden mobile card) and strict-mode locators fail otherwise.
- Absence assertions (`toHaveCount(0)`) prove role/organization boundaries; every gate should include at least one negative check.
- Success signals differ per dialog: some show a flash (`Kunde erfolgreich erstellt!`), some close immediately — assert the resulting row/state, not only flashes.
- Seeded identities use `@werkflow-golden.test` emails and org names prefixed `Golden Test SHK` / `Fremde Firma`; the invite scenario additionally uses Resend's bounce-safe test address pattern `delivered+gg-<runId>@resend.dev` so the real invite email sends without harming sender reputation. The leftover cleaner keys on exactly these markers. Never use these markers for real data.
- `tests/golden/support/db.ts` holds read-only service-role lookups for assertions the UI cannot prove (the invite code inside the email link, stock-ledger consistency). Specs still drive every user-visible action through the UI.
- **Specs inherit state from every earlier spec** (serial, alphabetical, one shared world): members joined in `@P1-03`, schedules and the holiday calendar from `@P1-04`, and so on. A step that passes in a focused run can legitimately fail only in the full run because names appear in more places or extra action buttons exist — that is the full run doing its job. Scope locators semantically (the exact section/row, `exact: true` names), never by count or position. State `@P1-06` leaves behind: `leave_approval` ends in `selected` mode with the admin as sole holder (Büro and the invited Büro member lost it), the employee has an extra Vollzeit condition valid from the run day + 1 carrying 30 vacation days, the employee keeps one approved future half-day vacation and one rejected request, and Büro keeps one approved future single-day vacation.
- **`GG-02` placement and dual-mode design (P1-07):** the gate spec lives in `p1-07.spec.ts` so it sorts AFTER every slice spec — it inherits the full suite-end state instead of injecting business facts that six earlier specs would silently inherit (the rejected alternative was seeding dedicated fixtures and running the gate early). Because the validation ladder also runs it focused on a fresh world, the spec is deliberately dual-mode: its first test pins the responsibility state itself (`time_approval` → employee sole, `leave_approval` → admin sole — a recorded no-op re-selection in the full run), it creates and closes its own client request instead of relying on GG-01's leftover, and every count expectation (inherited notifications, unified badge numbers) is derived from the database at runtime rather than hardcoded per mode. State `@GG-02` leaves behind (nothing runs after it, but seeder/`KEEP_WORLD` debugging should know): two extra no-op responsibility configurations, one closed GG02 client request, new schedule versions valid from run-day+1 for the employee (Mo–Fr 6h) and Büro (Mo–Fr 8h), one approved Büro manual time entry from yesterday 10–11, and for the employee one extra withdrawn, one cancelled, and one rejected vacation request plus attention read markers/events.
- **Date expectations come from the app's own stored state and in-code rules**: `@P1-06` reads the person's schedules/conditions/holiday calendar through `getTargetContextForRecord` (`tests/golden/support/db.ts`) and computes consumed days and weekly Soll with the same `lib/vacation/balance` and `lib/personnel/targets` functions the product uses — hand-rolled date logic in specs drifts in holiday weeks.
- **Expect Realtime-driven re-renders mid-step.** Re-locate a row after any mutation that re-renders it (a saved locator can hold a detached node), and never re-open or re-select a control whose desired value is already set — a router refresh can detach a Radix option between open and click.
- **Fixtures under uniqueness constraints must use dates no earlier spec owns.** Business facts like `employment_conditions`/`work_schedules` versions (unique per person + `valid_from`) or closure days (unique per org + date) collide deterministically in the full run when two specs pick the same date — @P1-09's fixture reused a run-day `valid_from` owned by an earlier slice and broke only in the full suite. Audit the inherited-state list for *date ownership*, not just locators and labels, and pick run-scoped or far-future dates (the @P1-09 fix uses run-day+90).
- **Stale-UI action proofs need a frozen page.** The app deliberately self-heals stale views (Realtime events plus a synthetic all-table refresh on `visibilitychange`), so a "click the stale card" test races the app's own freshness machinery and loses intermittently. `@P1-06` freezes the page first — `page.routeWebSocket` swallows the Realtime socket and an init script suppresses `visibilitychange` — which is also the honest simulation of the woken-up-laptop scenario the action-time enforcement exists for. This investigation surfaced a real defect: action-time authorization compared the app clock against database-stamped configuration timestamps, so a machine with a trailing clock briefly kept honoring a just-replaced configuration (fixed with a skew guard in `lib/responsibilities/server.ts`).

- **State `@P1-08` leaves behind** (P1-09 now inherits it): the employee carries one CANCELLED sickness report (yesterday–run-day, `krankheit`, evidence received; events `reported`→`ended`→`evidence_updated`×2→`cancelled` — it no longer affects any target), Büro carries one ACTIVE half-day `kind_krank` report for run-day−1 with evidence required/`pending` recorded by the admin (it halves Büro's yesterday target), and sickness read markers/`attention_events` exist for Büro (two versions of the employee report) and the employee (the cancellation). The spec pins NO responsibility state (sickness authority is the manager role); its mode-dependent expectations (vacation-overlap hint, weekly Soll, notification rows) are all derived from the database at runtime.
- **State `@P1-09` leaves behind** (P1-10 now inherits it): one active two-person team, one expired certification on the employee plus its renewed successor, one skill on Büro, two jobs with qualification assessments and reasoned overrides, an admin-enabled apprentice signal, a future apprentice condition/job at run-day+90, and qualification expiry read state/audit.
- **State `@P1-10` leaves behind** (it sorts last): one run-scoped customer with two contacts, a site, a linked job, communication defaults and contact overrides, audited guidance exceptions, one completed and two open follow-ups, follow-up lifecycle events, and attention read state as produced by the UI journey. The spec is dual-mode, uses no predecessor-owned effective-date keys, and derives identities from the run id.
- **P1-12 date ownership and state left behind** (`@GG-03` sorts last): the spec owns run-day+3 through run-day+10 at 06:00 Berlin (deliberately early so collisions with P1-11's 09:00+ next-month window, when the months overlap, only ever produce the reasoned-override warning that every planning step already handles), run-day+4 as the parked next-review date, and a run-keyed terminal Realtime job visit at run-day+8 08:00. It leaves behind four run-scoped jobs: the PARK job (scheduled run+3 06:00 after its unscheduled dispatch was traceably retargeted; parking context cleared with an `unparked` event), the MAIN job (one visit finally at run+7 06:00 with a 3-revision dispatch — issued → schedule_changed → schedule_changed —, one acknowledged/challenged/kept/re-acknowledged history, one superseded and one active customer commitment), the BATCH job (a two-occurrence daily series shifted to run+9/+10 as exceptions, its earliest occurrence dispatched with a pending confirmation), and the terminal LIVE job whose assigned visit and dispatch make the last test independently replayable. Batch/assessment/dispatch/parking/commitment event ledgers and attention read state exist as the UI journey produced them; no vacation/sickness/schedule/condition rows and no actual time entries were created. Future specs must address these records by run-scoped identities and must not assume an empty dispatch domain.
- **P1-13 Golden state left behind** (`@P1-13` sorts last): two run-scoped published templates (`Wartung <runId>` at versions 1 and 2, `Sanierung <runId>` at version 1), two jobs materialized from the two Wartung versions, and one project materialized directly from Sanierung. The first job has one employee-completed instruction; application/event/provenance rows remain. No inventory movement, reservation, planning occurrence, dispatch, actual time or document is created. Future last-sorting specs must use run-scoped identities and cannot assume an empty template domain.
- **P1-14 Golden state left behind** (`@P1-14` sorts last): four run-scoped jobs and one project, a closed job-linked time session with automatic execution event, one resolved employee blocker, one open manager parking blocker, and a reasoned project override followed by an override-clear event. No inventory movement, reservation, document, signature, message or customer package is created. Future specs must use run-scoped identities and cannot assume lifecycle tables are empty.
- **P1-15 Golden state left behind** (`@P1-15` sorts last): one run-scoped assigned job with a submitted and approved work report, one typed measurement artifact, exact immutable revisions/actions and lifecycle evidence/customer/signature gates. No planning or dispatch mutation, active time, inventory movement, commercial row, message or customer package is created. Future last-sorting specs must use run-scoped identities and cannot assume the artifact or evidence-fulfilment domains are empty.
- **P1-16 Golden state left behind** (`@P1-16` sorts last): one run-scoped assigned job and one denied unassigned job, completed instruction and execution state, one employee draft artifact, one contextual document link, one closed own time entry and paired take/return inventory movements. Stock returns to baseline and no active clock, copied work pack, reservation, consumption, commercial row, message or customer package remains. Future last-sorting specs must use run-scoped identities and cannot assume these job execution domains are empty.
- **Weekday-dependent expectations must be computed, not assumed.** The first Saturday full run (2026-08-08) exposed a latent weekend-blind assertion in `@P1-04`: after removing a Betriebsruhe day the spec expected „Tagesziel:", but on a schedule-free weekend day the dashboard honestly shows „Laut Arbeitszeitmodell heute kein Arbeitstag." The assertion now resolves today's target through `getTargetContextForRecord` + `resolveDailyTarget` and expects the matching text. Any assertion about "the day's target returns" must go through the resolver.
- **Mid-suite specs are not dual-mode.** Only the LAST spec file must pass focused on a fresh world; earlier specs may depend on their predecessors' state (`@P1-04`'s contract-mismatch hint needs `@P1-03`'s stored conditions and legitimately fails standalone). To verify a harness fix in a mid-suite spec, run the full suite — a solo focused run proves nothing and can fail for inherited-state reasons that are not defects.
- **Later specs must not reuse effective-date keys owned by earlier specs.** The first P1-09 full run exposed this with `employment_conditions`: P1-04 already owned run-day and run-day+1 versions, so adding another run-day condition was correctly rejected. A later slice that needs a new effective state must choose a non-colliding date and assess the dependent business action on that same date; P1-09 uses run-day+90 for its apprentice condition and planned job.

- **Manual time entries in specs must lie in the past.** The dialog rejects future times („Manuelle Einträge können nicht in der Zukunft liegen."), so a spec that runs in the morning fails with today's 09:00–10:00; use yesterday with times clear of other specs' yesterday entries (`@P1-05` uses 06–07 and 08–09, `@GG-02` uses 10–11).

### Remaining live-provider limit

Run archives, retained diagnostics, first-failure stopping and provider preflight reduce wasted replay and make failures attributable. They do not make a 40-minute serial journey against live Supabase and R2 deterministic. A connection can still fail after preflight, and one uninterrupted 105/105 run proves only that particular ordering and network window. Do not use the full battery as an iteration loop or erase this distinction by retrying until green. A future harness architecture decision should separate deterministic application certification from small live-provider canaries; until then, the long live battery remains a release integration signal with an explicit environment dependency.

The suite's default per-test budget is 180 seconds. At 87 serial live-project tests, the former 90-second budget produced unrelated navigation/dialog timeouts under accumulated host and network load even when focused inherited sequences passed quickly. Realtime-sensitive mutation helpers may retry one complete transaction only when a refresh demonstrably removed the UI before submission; after submission they must reassert persisted state rather than repeat the mutation. A missing live refresh may use one reload only where the authoritative persisted row is still asserted. These guards keep the business assertions strict without turning delivery latency into duplicate writes.
