# Security control map

Status: living — last reviewed 2026-09-18

Start here before adding a route handler, Server Action, privileged database call, storage path, or provider setting. This page names each security invariant, the mechanism that enforces it, and the check that catches a regression. It does not repeat environment facts ([environments](environments.md)), testing policy ([testing](testing.md)), or the finding log of the [2026-09 hardening pass](../plans/phase-1/hardening-2026-09/05-step-1-security-infrastructure.md); it links to them.

## Trust boundaries

| Boundary | What establishes identity and permission | Enforced by |
| --- | --- | --- |
| Route handlers (`app/api/*`, `app/auth/*`) | Each handler authenticates with `supabase.auth.getUser()` or delegates to an action that does. `POST /auth/callback` additionally requires a same-origin JSON request before it writes session cookies. | `lib/security/route-inventory.test.ts` lists every handler with its mechanism; a new handler fails the unit group until it is reviewed there. `lib/security/same-origin.ts` owns the origin check. |
| Server Actions | Exported actions and inline functions with `'use server'` are public POST endpoints. Establish identity and the required current role, organization, lifecycle, and object permission before a protected operation. The caller's ID comes from the verified session. | `lib/security/server-action-authorization.test.ts` discovers module and inline directives, rejects unsupported exports, and since 2026-09-13 fails on any exported action that no product module imports (Step 3 removed 41 such dead endpoints). Its helper-call check catches omitted identity checks, but does not prove ordering or correct permission checks. Negative boundary tests provide that evidence. Internal helpers belong in `server-only` modules such as `lib/members/queries.ts`. |
| Page routing | `proxy.ts` redirects cookie-less visitors away from every authenticated area; `app/(app)/layout.tsx` re-checks the session with `getUser()` and is the authority. | `lib/security/proxy-prefixes.test.ts` derives the required prefixes from the `app/(app)` folders. |
| Post-login redirects | Only same-origin paths may be used as return destinations; invite codes must be UUIDs before they are echoed. | `lib/auth/return-path.ts` with unit tests. |
| Organization context | The active organization cookie is a hint. `resolveActiveOrgId` accepts it only when the user is a current member; `setActiveOrgCookie` rejects unauthenticated/non-member writes. Client scope changes follow cookie confirmation. | `lib/org/cookies.ts`; request-only membership facts; `lib/data/membership-freshness.test.ts`, `lib/org/active-cookie.test.ts` and the organization component contracts. |
| Database | RLS restricts client table access. Security-definer functions in `public` revoke execution from `PUBLIC`, `anon`, and `authenticated`; privileged mutations use reviewed service-role calls. Ledger triggers also deny direct privileged UPDATE/DELETE. The 11 older event tables listed in migration `20260907010100_protect_existing_event_ledgers.sql` preserve their declared parent cascades and exact foreign-key nulling, while refusing unrelated nested mutations. | `sql:security` executes role, grant, challenge, ledger, and Realtime assertions. `canary:security` checks live DEV grants independently of local SQL. The Supabase security adviser provides additional configuration evidence; its RLS-without-policy INFO rows for `personnel_lifecycle_operations`, `email_change_challenges` and `app_private.email_change_send_windows` are not findings, because all three are service-role-only ledgers with no `anon` or `authenticated` grant (SEC-05, 2026-09-13). |
| Realtime | One channel per organization. RLS governs INSERT/UPDATE delivery. Raw DELETE and TRUNCATE publication are disabled; database triggers insert minimal deletion notifications into `realtime_deletions`, whose RLS checks current operational membership. Consumers receive invalidation signals and re-read through authorized readers. | `bun run realtime:check` checks publication flags, exact trigger coverage, and minimal replica identity. SQL and `canary:security` check foreign and revoked receivers. [Realtime and caching](realtime-and-caching.md) owns transport details and paired app/database rollout. |
| Files | Bytes live in private R2 buckets. Server code authorizes the target, generates the storage path, and signs a short-lived URL; finalization re-checks size and existence. Every storage key starts with the owning organization id, and since 2026-09-18 the signers (`createSignedUploadUrl`, `createSignedDownloadUrl` in `lib/storage/r2.ts`) take the organization id and refuse a key under another prefix, with a traversal or empty segment, or with an empty organization (`assertOrganizationStorageKey`, unit-tested in `lib/storage/r2.test.ts`); `headStorageObject` refuses malformed keys. A wrong caller can therefore never obtain a URL for another organization's object. Non-image, non-PDF types download as attachments. Three file classes exist: private R2 objects behind signed URLs, protected personnel documents (`P1-24`), and the public `profile-avatars` Supabase bucket (migration `20260906214500`), which holds avatars only. `lib/supabase/admin.ts` is `server-only`; the R2 adapter is banned from browser-reachable roots. `lib/storage/r2.ts` itself cannot carry `import 'server-only'`: Bun-run scripts, the preflight and the seed helper import it outside Next, where that package throws (tried and reverted, SI-010, 2026-09-06). | `lib/documents/upload-targets.test.ts`, document groups, canary C2; `lib/security/storage-import-boundary.test.ts` scans `app/`, `components/` and `hooks/` for any import of the adapter or the S3 SDK and is the boundary. |
| Email change | A service-role-only RPC serializes all challenge transitions per account. Challenge generations bind guesses and resends. Separate per-user current/new mailbox send timestamps in `app_private.email_change_send_windows` share the account lock and survive wizard reset, completion, and rejected-completion cleanup. A durable completion claim permits one Auth update and refuses replacement while its outcome is uncertain. Client roles cannot access either state table. | Migrations `20260907010000_atomic_email_change_challenges.sql` and `20260908120000_preserve_email_change_send_windows.sql`, `supabase/tests/email_change_boundaries.sql`, and `lib/security/account-boundaries.test.ts`. [The Step 1 record](../plans/phase-1/hardening-2026-09/05-step-1-security-infrastructure.md) distinguishes implemented controls and local evidence from deployment. |
| Mail | Both edge functions accept only the project's secret keys and HTML-escape interpolated values. The email-change code is stored as HMAC-SHA256 with the server secret `EMAIL_OTP_HASH_SECRET` over `${userId}:${code}` (`lib/settings/otp-hash.ts`, since 2026-09-18), so a leaked challenge table cannot be brute-forced and one user's hash never verifies another's code; the action refuses to run without the secret. Missing delivery configuration and provider failure return failure. Logs contain fixed error codes and status numbers, never recipients, OTPs, invitation URLs, or provider bodies. | Shared authorization, HTML escaping, and delivery boundaries under `supabase/functions/_shared/`; `lib/security/mail-handlers.test.ts` invokes the actual handlers with synthetic failures. |
| Browser | Responses carry `X-Frame-Options: DENY`, `Content-Security-Policy: frame-ancestors 'none'`, `X-Content-Type-Options: nosniff`, `Referrer-Policy: strict-origin-when-cross-origin`, and a minimal `Permissions-Policy`; Vercel adds HSTS as `max-age=63072000` without `includeSubDomains; preload`, and that stays so until every `werk-flow.app` subdomain serves HTTPS (decided 2026-09-06). Since 2026-09-18 the `Content-Security-Policy` header is the enforced origin-only policy `script-src 'self' 'unsafe-inline'; object-src 'none'; base-uri 'self'; form-action 'self'; frame-ancestors 'none'; report-uri /api/csp-report` (SEC-08, owner decision of 2026-09-18 after a report-only phase the same day that showed Next's inline scripts and Zod 4's caught `Function("")` probe and nothing else): browsers block scripts and plugins from any other origin and report violations to `POST /api/csp-report` through the legacy `report-uri` channel only, because Chromium batches `report-to` reports through the Reporting API and delivered none in the preview check; the handler is unauthenticated by design, reads and writes nothing, bounds the body and logs a redacted summary (`lib/security/csp-report.ts`, no script samples or query strings) that Vercel's runtime logs hold under `[csp-report]`. Injected inline scripts are not blocked; that gap is the nonce row in the [enforcement backlog](enforcement-ladder-backlog.md). Expected steady state of the log: one `eval` report per page load from Zod's probe (`blocked` `eval`, source a static chunk), which the policy blocks on purpose because Zod then parses without compiled code; verified on the enforced build on 2026-09-18 (login form validates, no console error). A report with any other `blocked` value is a finding. Authenticated cookie reads do not disable the generic PPR shell. The inspected production-build manifest marks `/auftraege`, `/kunden`, `/kalender`, `/inventar`, and `/dokumente` as `PARTIALLY_STATIC`; personalized content resumes behind the authenticated boundary. On 2026-09-14 the owner chose a report-only strict script policy first; [pre-Wave-3 step 5](../plans/phase-1/pre-wave-3/05-beta-acceptance-and-production-rollout.md) deployed it on 2026-09-18, production reported Next's streamed inline scripts (`script-src-elem`, `blocked` `inline`) and Zod's eval probe, and the owner chose the origin-only enforcement the same day. Any report naming another origin is a finding. A manifest entry alone does not prove cache confidentiality. | `next.config.ts`; `lib/security/headers.test.ts`. |
| Dependencies | `static:dependencies` performs a bounded network advisory check for dependency/gate changes and release mode. Unknown findings, changed applicability inputs, and expired exceptions fail. A network failure leaves the check unverified; offline unit success cannot replace it. | `bun run security:dependencies`, `lib/testing/dependency-audit.ts`, and exact reviewed exceptions in `lib/security/dependency-exceptions.json`. Unit fixtures check rejection paths without requiring network access. |

## Rules for new code

1. A `'use server'` file may only export functions that establish the caller identity first. Put helpers that need an admin client or a trusted user ID in a `server-only` module and import them.
2. A route handler needs a reviewed entry in `lib/security/route-inventory.test.ts` naming its authorization. Handlers that set cookies from a request body must call `verifySameOriginJsonRequest`.
3. A new public RPC that runs as `SECURITY DEFINER` must revoke `PUBLIC`, `anon`, and `authenticated` execution and grant `service_role` explicitly. Put required RLS helpers in `app_private` with reviewed client execution grants and named assertions. `app_private.get_user_org_ids(uuid)` is such a helper; it is not an exception for public RPCs.
4. Give new ledger tables a database trigger that denies direct privileged rewriting. Choose cascade/reference-nulling behavior from the domain's retention contract. Migrations `20260906213000_harden_security_boundaries.sql` and `20260907010100_protect_existing_event_ledgers.sql` contain the existing patterns. Add real denial and permitted-cleanup assertions to `sql:security`.
5. Return stable error codes for provider failures. Log only reviewed non-sensitive classifications and status numbers. Raw provider bodies can contain personal data or credentials.
6. Redirect destinations from query strings go through `resolveSafeReturnPath`.
7. The service-only `SECURITY INVOKER` list RPCs also revoke browser execution. Their authenticated server callers resolve organization and role before using the admin client. `sql:list-pagination` tests grants, tenant separation, employee visibility, whole-dataset filters, totals, and bounded pages. `canary:security` also checks that all five list RPCs exist on DEV, deny `anon`/`authenticated`, and grant execution to `service_role`.

## Known residual exposure

- Injected inline scripts are not blocked (SEC-08). The enforced script policy is origin-only with `'unsafe-inline'` (owner decision of 2026-09-18, an accepted limitation, not closure): it blocks scripts and plugins from foreign origins but an attacker who can place an inline script into a page still runs it. Closing the gap needs the nonce policy: a token per request generated in `proxy.ts`, every authenticated page rendered per request so the static shells leave the CDN cache, and the eleven performance references re-measured. Open row in the [enforcement backlog](enforcement-ladder-backlog.md); violations of the enforced policy are read in Vercel's runtime logs under `[csp-report]`.
- Member removal refuses targets with recorded time. `P1-33` still owns complete offboarding and asset return.
- No general application-level rate limiter. Supabase Auth limits cover its own endpoints, not the service-role Edge Functions that send through Resend. Custom email-change guesses have an atomic per-challenge cap; its 60-second per-mailbox send windows persist outside challenge state. The latter repair reached DEV in commit `136f529` and PROD on 2026-09-18 with the beta release ([step 5](../plans/phase-1/pre-wave-3/05-beta-acceptance-and-production-rollout.md)). Broad edge rate limiting remains the owner's separate Vercel plan decision.
- The deletion transport permits current organization members to receive minimal deleted-row identities. This does not grant access to record contents. It is live on PROD since 2026-09-18; the [step 5 run log](../plans/phase-1/pre-wave-3/05-beta-acceptance-and-production-rollout.md#run-log-2026-09-17-2314-utc-onwards-the-night-of-2026-09-18-in-berlin) holds the direct receiver evidence on PROD.
- `simulatePayment` in `lib/subscription/actions.ts` lets any authenticated user activate their own organization's subscription. It stays as the beta activation path until a real price exists (owner decision 2026-09-14) and closes with the payment slice.
- The 2026-09-08 repair audit found no dependency advisories after compatible nested tooling updates. `lib/security/dependency-exceptions.json` is empty. Future exceptions require exact paths, applicability reasoning, the dependency digest, and expiry. Runtime dependencies cannot be dismissed as tooling. Reassess when imports or build-input trust change.
- Two inspection gaps from the 2026-09 hardening pass stay unverified. The full R2 bucket CORS configuration: the object-scoped credentials cannot read it, and the only evidence is a signed-preflight observation for a synthetic path that allowed the production origin for GET, PUT and HEAD and rejected an unrelated origin with 403 (`.agent-logs/r2-cors-observation.json`), which is behavior evidence for those origins, not a configuration export. Vercel environment-variable scoping: the session had no admin token, so no secret-routing claim follows from deployment readiness.

Recovery, monitoring, and incident handling live in [recovery-and-incidents](recovery-and-incidents.md).

## Revocation boundaries

| Consumer | Enforcement and limit |
| --- | --- |
| Privileged server reads and actions | Verified Auth identity plus current operational membership, role, object, and lifecycle rules. Membership, role, lifecycle and blockers reload on each request/render; scheduled restrictions are evaluated at read time. Mutation tags still invalidate affected rendered content. A local SQL test does not prove browser refresh or transaction-time authorization. |
| Direct database clients | RLS consults current membership and effective personnel access. The `sql:p1-24` group checks the lifecycle restrictions. JWT validity alone does not grant organization access. |
| Realtime | INSERT and UPDATE use current table RLS. Deletion notifications need the separate protected transport described in [realtime-and-caching](realtime-and-caching.md). Same-organization freshness is not tenant-denial evidence. |
| Already-issued signed file URLs | URLs are bearer capabilities. Revocation prevents new signing, but an existing download URL lasts up to 10 minutes and an upload URL up to 30 minutes under the current defaults. Finalization checks authorization again. Previously downloaded files cannot be recalled. Do not promise immediate revocation of issued URLs. |
| Auth sessions | [Supabase sign-out semantics](https://supabase.com/docs/guides/auth/signout) allow an issued access token to remain valid until expiry. Suspend operational access during an incident and use the [runbook](recovery-and-incidents.md). Identity validation with `getUser()` is not proof of immediate session termination. |

## Sensitive-data handling and owner decisions

| Data | Current purpose and access | Retention responsibility |
| --- | --- | --- |
| Customer contacts, sites, work records, and signatures | Organization operations. Roles and assignments restrict reads and writes; database metadata and private file bytes have separate providers. | Preserve business history and explicit trash/version behavior. The owner must set contractual retention/deletion rules before client data is imported. Do not add guessed automatic deletion periods. |
| Personnel, sickness, time, and payroll exports | Employment operations. Personnel access classes and explicit releases are separate from the ordinary document library. Exports become copies outside app access control. | The owner decides the lawful purpose, recipients, and retention with appropriate advice. Ending access does not authorize deleting employment or time history. |
| Mail | Invitations and OTP delivery through Resend; no business documents are sent by these handlers. | Provider mail metadata has its own lifecycle. Never log invitation capabilities, OTPs, or recipient addresses as diagnostic success output. |
| Logs, traces, and test artifacts | Diagnosis and test evidence. Test fixtures are synthetic; local `.agent-logs` is ignored by Git. | Limit access and remove raw secrets from exported evidence. There is no claim that ignored files are encrypted or automatically purged. Incident evidence retention is an owner decision. |
| Backups and retained file versions | Recovery, distinct from the live record's visibility. Database backups do not contain R2 bytes. | [The runbook](recovery-and-incidents.md) records actual backup coverage, accepted loss, and provider-rehearsal triggers. Deleting a live record does not erase a retained backup. |

## Clock-state reads

The global clock and active-job badge read through `GET /api/time-tracking-state`. Both the canonical clock Server Action and its aggregate caller check current organization membership before reading retained sessions or settings with the service role. Authentication alone does not authorize a removed employee's retained session. `lib/time-tracking/state-http.test.ts` invokes both actual actions with denied identities and verifies zero protected reads. The global clock/badge GET adds active-organization equality and validates its read kind; it does not replace the actions' own permission checks.

## Read-request authorization reuse

`GET /api/customer-page` follows the same request lifetime. It validates the single organization/page/search values, checks current operational membership and manager role, and requires the requested organization to equal the resolved active organization before calling the internal paged reader. That resolution is `resolveActiveMembership`: the stored cookie organization when it names a current operational membership, otherwise the caller's first current membership, so a stale cookie can only select an organization the caller still manages. Initial page rendering authorizes before using that same reader. Actual route tests reject anonymous, employee, removed and foreign requests without protected reads, and preserve sanitized private errors.

`GET /api/background-read` (pre-Wave-3 step 3) runs one of the readers registered in `lib/data/background-reads.ts`: the kind must exist in that closed registry, the input must pass the kind's schema, the cookie session must authenticate, and an input that names an organization must equal the resolved active organization; every reader keeps its own membership and subject checks, and a thrown reader returns `unexpected_error` without its message. `lib/data/background-read-http.test.ts` proves the denials before any reader runs. Adding a kind is adding a public read endpoint: the reader must authorize on its own.

`GET /api/calendar-board` (`P1-24a`) returns the Plantafel context for one organization and window: employee rows, daily targets with absence and pending-vacation facts, dispatch states per recipient and the job ids with planned material. It requires the requested organization to equal the resolved active organization; an employee receives only their own row, days and dispatch states, and a stranger an empty success. `lib/calendar/board-http.test.ts` proves the outsider denial and the employee narrowing through the real handler. `saveCalendarPreferences` (`lib/calendar/preferences-actions.ts`) writes only the caller's own row of `organization_user_preferences`, keyed by the resolved organization and user, after schema validation.

The calendar-window, calendar-board, attention-count, time-tracking-state and background-read GET handlers use `lib/data/read-request-cache.ts` to share repeated `getAuthenticatedUser` and `getCachedMemberships` calls within that one read. Each GET receives a fresh asynchronous scope. Neither identity promises nor membership candidates cross requests. Membership candidates use the same request/render lifetime; their former persistent cache was removed after it caused fallback to overwrite a newly created organization cookie. The backend scheduler preserves the original asynchronous request context when queued work resumes, verified in `lib/supabase/request-scheduler.test.ts`. Its capacity and fairness rules live in [Realtime and caching](realtime-and-caching.md#backend-request-capacity). The wrapper rejects non-GET requests. Do not wrap a Server Action or mutation in it, and do not pass caller-supplied trusted authorization context into a `'use server'` export.

The same GET scope shares `loadResponsibilityRuntimeState` by organization so parallel attention derivations read permission facts once. That reader explicitly uses `outsideRequest: 'fresh'`: Server Actions and calls outside a GET always read again. A later GET also reads again. No cross-request permission cache is introduced.

The privileged profile lookup deliberately uses a fresh caller-scoped RLS read on every call. Never replace that check with a potentially stale authorization cache, and never cache authenticated responses at the CDN: every authenticated GET here returns private, non-cacheable responses (Step 1 handoff, 2026-09-08).

The scope carries the originating GET's abort signal into server-side Supabase fetches. An abandoned read cancels only its own downstream requests. Caller cancellation and the existing timeout remain effective; mutations outside the scope inherit no GET signal. Client live views abort obsolete GET reads while retaining generation checks for transports that cannot cancel.

`lib/data/read-request-cache.test.ts` pins the reviewed consumers. The calendar HTTP fixture exercises the real route, aggregate and authorization helpers with provider boundaries, including fresh denial on later requests. `read-request-lifetime.test.ts` exercises the actual responsibility reader and fetch wrapper: shared concurrent reads, separate organizations, fresh later permissions, failures and isolated cancellation. Extending this optimization requires reviewing the new read boundary and extending these checks. [React's cache reference](https://react.dev/reference/react/cache#pitfall) explains why route handlers need their own request lifetime.
