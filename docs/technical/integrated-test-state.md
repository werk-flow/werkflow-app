# Integrated test state

Status: living — last reviewed 2026-09-06

This reference owns the fixture state and date constraints within connected Golden journeys. Use [testing.md](testing.md) for execution and acceptance policy.

Read this reference when changing the integrated Golden journey or its declared producer dependencies. The complete journey retains earlier records unless a later spec changes them. Independent audit groups do not inherit this state. A separate Golden group runs only its declared prerequisite files, so it must not assume every earlier file ran. Keep durable fixture constraints here and acceptance history in the slice records.

- Golden specs inherit state from preceding files, including P1-03 members and P1-04 schedules. Scope locators to the exact row or section because full-run state can contain additional matching names. `@P1-06` leaves `leave_approval` in `selected` mode with Admin as sole holder, an employee condition valid from run-day+1 carrying 30 vacation days, an approved employee half-day vacation, a rejected employee request, and an approved Büro single-day vacation.
- **`GG-02` placement and dual-mode design (P1-07):** the gate spec lives in `p1-07.spec.ts`, after P1-03 through P1-06 and before P1-08 onward. It inherits its predecessors' state and leaves its own changes for later specs. Because the validation ladder also runs it focused on a fresh world, the spec is deliberately dual-mode: its first test pins the responsibility state itself (`time_approval` → employee sole, `leave_approval` → admin sole — a recorded no-op re-selection in the full run), it creates and closes its own client request instead of relying on GG-01's leftover, and every count expectation (inherited notifications, unified badge numbers) is derived from the database at runtime rather than hardcoded per mode. State `@GG-02` leaves behind: two extra no-op responsibility configurations, one closed GG02 client request, new schedule versions valid from run-day+1 for the employee (Mo–Fr 6h) and Büro (Mo–Fr 8h), one approved Büro manual time entry from yesterday 10–11, and for the employee one extra withdrawn, one cancelled, and one rejected vacation request plus attention read markers/events.
- **Date expectations come from the app's own stored state and in-code rules**: `@P1-06` reads the person's schedules/conditions/holiday calendar through `getTargetContextForRecord` (`tests/golden/support/db.ts`) and computes consumed days and weekly Soll with the same `lib/vacation/balance` and `lib/personnel/targets` functions the product uses — hand-rolled date logic in specs drifts in holiday weeks.
- **Expect Realtime-driven re-renders mid-step.** Re-locate a row after any mutation that re-renders it (a saved locator can hold a detached node), and never re-open or re-select a control whose desired value is already set — a router refresh can detach a Radix option between open and click.
- **Fixtures under uniqueness constraints must use dates their spec owns.** Business facts such as `employment_conditions` and `work_schedules` versions, or closure days, collide deterministically when two specs pick the same date. Claim audit offsets through `ownedBerlinDateAtOffset()` in `tests/golden/support/date-ownership.ts`; it throws when a spec uses another spec's range. Use `dispatchOverviewBerlinDateAtOffset()` for a visit that must appear in the manager dispatch panel. It rejects offsets outside the product's shared 0 through 14 day window. Golden offsets remain documented below because their earlier specs predate that registry.
- **Stale-UI action proofs need a frozen page.** The app deliberately self-heals stale views (Realtime events plus a synthetic all-table refresh on `visibilitychange`), so a "click the stale card" test races the app's own freshness machinery and loses intermittently. `@P1-06` freezes the page first — `page.routeWebSocket` swallows the Realtime socket and an init script suppresses `visibilitychange` — which is also the honest simulation of the woken-up-laptop scenario the action-time enforcement exists for. This investigation surfaced a real defect: action-time authorization compared the app clock against database-stamped configuration timestamps, so a machine with a trailing clock briefly kept honoring a just-replaced configuration (fixed with a skew guard in `lib/responsibilities/server.ts`).

- **Weekday-dependent expectations must be computed, not assumed.** The first Saturday full run (2026-08-08) exposed a latent weekend-blind assertion in `@P1-04`: after removing a Betriebsruhe day the spec expected „Tagesziel:", but on a schedule-free weekend day the dashboard honestly shows „Laut Arbeitszeitmodell heute kein Arbeitstag." The assertion now resolves today's target through `getTargetContextForRecord` + `resolveDailyTarget` and expects the matching text. Any assertion about "the day's target returns" must go through the resolver.
- Dependent stages retain `requireVisiblePrecondition`, `requireSerialPrecondition`, or `requireChainedValue` checks from `tests/golden/support/preconditions.ts`. Their errors identify the missing fact and recovery chain. Static annotations reject known incomplete fresh selections earlier. Both checks are needed: selected producers can still fail to establish the expected state.
- **Later specs must not reuse effective-date keys owned by earlier specs.** The first P1-09 full run exposed this with `employment_conditions`: P1-04 already owned run-day and run-day+1 versions, so adding another run-day condition was correctly rejected. A later slice that needs a new effective state must choose a non-colliding date and assess the dependent business action on that same date; P1-09 uses run-day+90 for its apprentice condition and planned job.

- **Use past dates for ordinary manual-entry fixtures.** Unless a scenario explicitly tests an allowed future-date path, use yesterday with times clear of other specs' entries. Today's 09:00–10:00 is still in the future during an early run. `@P1-05` uses 06–07 and 08–09; `@GG-02` uses 10–11. The legacy validator has an explicit admin future-date exception, and P1-22 correction fixtures deliberately use a future date. Those scenarios follow their owning date contracts.
