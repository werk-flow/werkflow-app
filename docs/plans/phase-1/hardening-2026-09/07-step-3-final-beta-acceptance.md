## PPR and script policy

Evidence from the last recorded production build (`98d6ea47-28fe-454f-b7ec-daeafcadb090`, cache components on):

- The prerender manifest marks every route, including every authenticated route, `PARTIALLY_STATIC`. The static shells on disk (`.next/server/app/kunden.html`, `auftraege.html`, `kalender.html`, about 5.5 KB each) contain the generic app-shell skeleton, one inline script (the framework's `requestAnimationFrame` timing snippet), 32 to 34 external script tags, no nonce attributes and no user, organization or customer strings. The `.meta` files carry `x-nextjs-prerender: 1` and `x-nextjs-stale-time: 300` with no personalization. Personal content resumes behind `AppProviders`, which awaits the cookie-bound identity read, so by construction the shell cannot contain it.
- `proxy.ts` redirects cookie-less requests to `/login` before any shell is served for the protected prefixes, now including the time-tracking subroutes (SEC-06).
- The resumed part of every authenticated page streams the RSC payload as inline `<script>` elements. Those are per-request and cannot be hashed at build time.

Framework facts, verified against the Next.js 16.3 content-security-policy guide on 2026-09-13: nonces require dynamic rendering and are explicitly incompatible with Partial Prerendering because the static shell's scripts cannot carry a request nonce; the documented alternative that keeps static output is `script-src 'self' 'unsafe-inline'`; the experimental SRI feature hashes external bundles only and "cannot handle dynamically generated scripts".

The choice is therefore binary and belongs to the owner:

1. Nonce policy (`script-src 'self' 'nonce-…' 'strict-dynamic'`) generated in `proxy.ts`. Real XSS mitigation. Every authenticated route becomes fully dynamic: the generic shell is no longer served from the CDN cache, first paint waits for the server, and the eleven performance references need re-measurement on the new rendering. Public pages (`/login`, `/signup`) become dynamic too.
2. Origin-only policy (`script-src 'self' 'unsafe-inline'; object-src 'none'; base-uri 'self'; form-action 'self'` plus the existing `frame-ancestors 'none'`). Keeps PPR and the measured performance. Blocks injected external scripts, plugins, base tag hijacking and cross-origin form posts, but does not block injected inline scripts; the plan's own rule that "a permissive script policy added solely to keep PPR is not closure" applies, so this option must be recorded as an accepted limitation, not as closure.
3. Report-only deployment of option 1 for one preview cycle to measure hydration, streamed scripts and third-party breakage before choosing.

No policy change was made in Step 3; `next.config.ts` still carries the Step 1 headers. Recommendation: option 3 on the next `partner-preview` publication, then option 1 unless the measured first-paint cost on the beta business's office devices is unacceptable, in which case option 2 with the limitation recorded in [security](../../../technical/security.md). Preview shares PROD, so the report-only header is the safe first step: it changes no behavior and produces browser reports without blocking anything.
