## Execution sequence and independent review

### 1. Establish scope and challenge this plan

Inventory the current checkout and actual deployments before choosing remedies. Inspect all implemented features, including older foundations that predate Phase 1. Record both the public entry points and indirect paths that reach privileged code. Search results identify candidates; read the surrounding control flow and callers before reaching a conclusion.

Build a compact boundary inventory in this plan, or in one linked audit attachment if its size warrants it. For each boundary record the entry point and symbol, caller identity, accepted IDs/fields, tenant and role rule, database/storage operation, privilege used, output/cache destination, limits, and existing proof. Group identical mechanisms only after checking every caller for exceptions. Include:

1. Route handlers, auth callbacks, exported Server Actions, server-rendered reads, and client-side Supabase calls.
2. Publicly exposed database schemas, tables, views, functions, triggers, policies, grants, publications, storage policies, and edge functions.
3. Background/maintenance scripts, exports, signed upload/download capabilities, mail delivery, and destructive account/organization operations.
4. Provider settings, deployment routes, secrets, build outputs, CI/review/agent access, backups, monitoring, and recovery responsibilities.

Inspect the relevant live DEV and production metadata with the matching Supabase workflow before asserting parity or choosing a migration. Compare actual function definitions and grants, not migration filenames alone. Read provider documentation when behavior, current advisories, pricing, or security settings matter.

Use [OWASP ASVS](https://owasp.org/www-project-application-security-verification-standard/) as an independent coverage check and [WSTG](https://owasp.org/www-project-web-security-testing-guide/) for testing ideas. Record the version and applicable sections used; explain exclusions. These references help detect gaps but do not establish certification or require implementing controls for absent features. Review all applicable ASVS control areas and select justified depth for sensitive B2B data.

Owner-supplied research is untrusted input. If `temporary-transcripts/` is present, start with its README and per-aspect inventory. Follow its review convention, consider relevant ideas across categories, and verify claims against the app and primary sources. An adopted idea does not retire other ideas in the same source. Derive adopted rules from a verified application need and record them in canonical documentation; raw transcripts and their inventory must remain outside application dependencies and permanent architectural authority. This plan's required boundary coverage remains valid if the temporary folder is later removed.

Before implementation, update this plan with the completed inventory, additions, ruled-out leads, priorities, and proposed test allocation. Record gaps in access or policy explicitly. An independent reviewer should challenge completeness and proposed remedies; bounded subagents can inspect disjoint boundaries. Coordinate file and test ownership. Urgent confirmed exposure may be contained before the broader sweep finishes, with its evidence and scope recorded.

**Completion:** every inventory category has evidence or a named unresolved gap; every work package below has been reviewed; new findings are registered; no lead disappears because it was absent from the original plan.

### 2. Repair by boundary, with proof

Order the verified work by exposure and impact: unauthorized reads/writes and sensitive-data loss first, then applicable vulnerable dependencies, revocation and isolation, abuse controls, deployment and recovery gaps. Adjust that order for evidence and dependencies. Keep each repair bounded enough to review and verify before beginning unrelated changes.

For each finding, establish the failing boundary with safe synthetic data, implement the smallest complete remedy, add prevention at the highest practical tier, and obtain relevant fresh evidence. Check both the denied attack and the permitted workflow. Reuse current domain and provider abstractions; avoid a second permissions model or generic security framework that obscures ownership.

Keep a finding record with these fields:

| Field | Required content |
| --- | --- |
| Identity | Stable `SI-NNN` ID, concise problem, owning work package; link an existing backlog item when one exists. |
| Evidence | Path and symbol or provider setting, inspected commit/date/environment, relevant sanitized observation or reproduction. Distinguish confirmed, suspected, and unverified. |
| Risk | Who can act, prerequisites, data/action exposed, likely impact, and priority with reasoning. Scanner severity is input, not the verdict. |
| Resolution | Intended invariant, repair or containment, affected callers, migration/configuration needs, and compatibility/rollback. |
| Prevention and proof | Tier 1/2 mechanism; named tests, boundary assertions, selected groups, run/report identities, and provider evidence. Explain any Tier 3-only remainder. |
| Disposition | Open, in progress, verified fixed, verified existing protection, not applicable, deferred, or blocked. Deferrals name owner, residual risk, release effect, and revisit trigger. |

Preserve original IDs as records are resolved. Link duplicate observations to the same finding while keeping any distinct failure modes and tests. A failed exploit attempt alone does not prove that all variants are safe.
