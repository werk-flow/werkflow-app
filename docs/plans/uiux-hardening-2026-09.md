# UI/UX Hardening 2026-09

Status: closed (2026-09-04) — all six phases complete

Owner-directed pass between the Wave 2 acceptance and the beta-client handoff. The 2026-08 consolidation ([uiux-consolidation.md](uiux-consolidation.md)) wrote the canon and migrated the surfaces that existed then; sixty-one UI files shipped after it. This ledger records what a fresh audit found on 2026-09-03, whether each finding was missed by the consolidation, a regression against a written rule, or a rule the canon never stated, and what climbed the enforcement ladder ([decision 0005](../decisions/0005-enforcement-ladder.md)). The canon itself lives in the `werkflow-design` skill; this file is the record, not the rule.

## Owner rulings (2026-09-03)

1. Custom controls on every viewport of the web app; native pickers belong to the future React Native app only.
2. Time rules move into the Zeiterfassung area as a real subpage; Settings links there. No area tab leaves its area.
3. Every field renders through `Field`; required fields carry the marker; submit buttons are never pre-disabled as a validation hint (exception: forms with at most two obvious required fields).
4. Rows that do nothing on click have no hover, and neither do their skeletons.
5. No page-level horizontal scroll on any viewport; tables get card layouts below the tablet breakpoint; nothing is cropped to comply. Named exceptions: calendar day and week grids, the signature pad.
6. Focused browser proofs after each phase on the local stack; the full certification runs once at the end of the thread.
7. The whole pass runs on the recommended basis, start to finish, in one session.

## Phases

Each phase ends with lint, typecheck, the unit suite, `docs:check`, a focused browser proof of the touched areas on the local stack, and a commit pushed to `partner-preview`.

- [x] **Phase 0, live defects.** Findings 1, 6, 7, 8, 9. Proof: `@GG-00`.
- [x] **Phase 1, canon and primitives.** Canon amendments in the skill; primitives and hooks from findings 2, 3, 13, 14, 15, 17; the label lint and the uuid lint; the 23 glued labels fixed. Proof: `@GG-00`, `@P1-13`.
- [x] **Phase 2, layout.** Every page onto the shell (raw column literals now lint-banned); Service and Zeiterfassung `layout.tsx` with `AreaNav`; time-account rules moved to `/zeiterfassung/einstellungen` with Settings linking there; content-only subpage loading states; headers outside the data boundary on Aufträge, Anfragen, Arbeitsvorlagen and the service lists; inventory, member, invitation, document and job tables with card layouts below `md`; the settings shell on the primitive. The calendar header intentionally remains inside its data boundary because it is bound to container state. Phase 4 later replaced the temporary fixed-width detail skeletons. The durable canon now states the implemented hierarchy: an area layout renders the area name as its `h1`, and each subpage renders its own `h2`.
- [x] **Phase 3, forms.** Every label-plus-control stack in `app/` and `components/` is a `Field` (about 400 stacks across 110 files), with required markers, helper text and field errors wired through it; the registry controls read the `Field` context for id and ARIA. Every inline error is `ErrorText`; region failures are the new `SectionError` with retry; lint bans raw `role="alert"` outside the primitives. Submit buttons no longer pre-disable as a validation hint (owner ruling 3; forms with at most two obvious required fields keep enable-on-completeness); missing input marks the field and focuses it. Sixteen entity or long-enum selects are searchable (service dialogs, artifacts, inventory unit and CSV mapping); the avatar zoom is a `QuantityStepper`, the inventory billable flag a `Checkbox`; lint bans native checkbox, radio, range, month and week inputs. The delete-organization footer uses `AlertDialogAction`. Textarea `rows` is gone. Spec interactions for the migrated selects were adapted in place. Phase 4 closed the one deferred accessibility detail by placing the email-change OTP slots inside a labelled `Field`.
- [x] **Phase 4, skeletons and hover.** Every list declares its column definition once and exports one skeleton component built from it (Kunden, Mitarbeiter, Einladungen, Anfragen, Aufträge with its visible-column filter, Dokumente library and work context, entry history, inventory movements, the period result table); the loading-state files and the detail loading files render those components instead of hand-built rows, and the Aufgaben, Arbeitsvorlagen and Qualifikationen skeletons mirror their real card structure. The three Zeiterfassung lists the old skeleton file described as tables are header-less bordered rows, so their skeletons now mirror that shape instead. Hover exists only through `interactive`: the `hover:bg-accent/50` literal and cursor or hover classes on `TableRow`/`ListRow` are lint-banned outside `components/ui` (Tier 2), Anfragen, Personalakten, Dokumente, project child jobs, equipment and service-case link lists and the dashboard menu tiles moved onto the primitives, and `ListRow` gained a `plain` variant for rows inside a divided card (the Aufgaben task links). State tints layered on a selected or dragged document row live in named constants. Sixteen spinner-only or text-only section loads became section skeletons (job picker, both qualification sections, artifacts dialog, time-correction dialog and list, dispatch readiness, evidence list, document link catalog, versions, history and preview). `lib/ui/skeleton-pairing.test.ts` pins the pairing (Tier 2): loading files carry no table imports, hand-built rows or hover classes, and every column definition feeds both header and skeleton, with one named exemption for the inventory movements tab that has no loading state. The Phase 3 leftover closed: the email-change OTP slots sit in a labelled `Field`. The proofs also caught three Phase 3 collisions between the development-time option-count guard and ten-option fixed enums (blocker reason, parking reason, service-case status filter); all three are `SearchableSelect` now, per the registry rule, and their eleven spec sites select through the shared helper. Accepted for closure: option rows inside pickers (document link, attach, job materials) keep their own muted hover tokens because they are buttons, not list rows.

## Phase 6 retrospective and corrected closure method

Phase 6 was not a normal certification cycle. Between `2026-09-03T221321932Z-356ccf` and the deliberate stop at `2026-09-04T130118520Z-5e9bc2`, 21 complete-battery attempts recorded 546.5 minutes (9.11 hours) of machine test time: five Golden runs and sixteen audit runs. Golden failed twice on real pending-boundary defects, then passed 142/142 three times in 29.4 to 30.6 minutes. Those passes were valid for their fingerprints, but later application corrections made them stale for final acceptance. Audit failed 15 times — ten stale or coupled harness assumptions and five product defects — before the sixteenth run was stopped at 47/149 with zero failures, classified as an operator-cancelled environment run, and cleaned. The [incident log](../technical/test-incident-log.md#phase-6-certification-campaign-and-stop-decision) records every run, fingerprint, world, root cause, correction and cleanup.

After the static reconciliation and focused closure proofs, audit `2026-09-04T152646760Z-e9ead5` reached 146/149 before retaining a sixth product defect. Period preparation applied a December approved correction to an August legacy sequence, so the later `clock_out` falsely closed the open August entry, removed the required close blocker and attributed 2,649,600 source seconds to August. The correction is product-side and period-safe: apply the full correction chain, then re-bound projected facts to the period input window before pairing or missing-clock detection. A pure unit regression owns both the false-close case and the valid move-out-of-period case; the exact P1-23 producer/consumer proof passed on the corrected source.

The next audit `2026-09-04T164752977Z-210e39` stopped at 33/149 on a seventh product defect: Aufträge rendered a newly created project from its client-owned live collection, but the next creation dialog still received the initial server props and could not select that confirmed project. The dialog now receives confirmed live/overlay jobs and projects while pending temporary ids remain unselectable (Tier 1). Current-source A1 proof passed 28/28, and the explicitly justified final audit `2026-09-04T171146002Z-0606f9` passed 149/149 on production build `E2sUR-Q2cu1rX_DtB0kAP`.

Golden then found a test-only boundary at 126/142 (`2026-09-04T182505626Z-445923`): the shared work-pack helper queried the whole document and collided with a hidden Next.js transition copy outside the one visible semantic `main`. Scoping the helper to `main` removed that ambiguity. Retained replay exposed a second harness gap: the P1-20 field stage was not idempotent after its first attempt had already persisted the employee assignment. The stage now reuses that named assignment when present. The retained diagnostic passed 1/1, a fresh P1-20 chain passed 5/5, the complete Golden battery passed 142/142 (`2026-09-04T190428385Z-44080d`), and the rebuilt DEV cloud canary passed 9/9 (`2026-09-04T193601186Z-6acc27`).

The Golden harness correction changed the source fingerprint after the complete audit, but did not change application code or the production build. An additional current-source audit-consumer run was attempted for every importer of the changed helper. Its one created world was invalid because the local run served the preceding cloud-target build; it was classified `environment` and cleaned. Two subsequent attempts were refused before world creation as the WSL NAT address changed repeatedly and the local Supabase containers restarted. Closure therefore does not claim a shared final audit/Golden fingerprint: it records full audit evidence for the unchanged product build, final-harness Golden and canary evidence, and the exact environment limitation. Repeating a 149-test audit against a collapsing local backend would have tested availability luck, not UI/UX correctness.

Golden completed comparatively quickly because it is a compact, incrementally maintained critical-path battery: 25 specs, 6,782 lines, 142 tests and a 180-second scenario budget. Audit is a retroactive exhaustive catalog: 20 specs, 14,093 lines, 129 declarations expanded to 149 tests and a 240-second scenario budget. Both are serial and stateful, but audit consumers more often inherit one mutable world's state from distant producer tests. This pass changed form semantics, accessible labels, picker interaction, headings, row navigation and asynchronous settlement across the application. Stale audit contracts therefore surfaced one at a time and often late. The five product findings justified the audit; using the entire audit as the discovery loop did not.

The stop decision preserves the accepted test model. Nothing in this UI/UX pass removes the three-tier enforcement ladder, Golden/Audit/Canary responsibilities, audit flow IDs, business assertions, fresh production-build rule, local/cloud separation, retained-world evidence or classification discipline. The correction for this pass is narrower:

1. Reconcile all 17 findings against code, canon, architecture, historical feature docs and the enforcement backlog before another browser battery.
2. Run static enforcement and focused browser proofs against the final source for the contracts changed during closure.
3. Freeze application, harness and build-input files.
4. Run exactly one bounded final local audit and Golden pair on that fingerprint, followed by the unchanged DEV cloud canary.
5. If a battery fails, stop at the first retained failure and diagnose it. Do not authorize another complete run until the exact boundary has a current-source focused proof and the rerun policy permits it.

The separate pre-Wave-3 test-system overhaul owns the structural repair. Its starting requirements are now explicit: audit tests must either own their setup or declare machine-checkable checkpoint prerequisites; retained diagnostic stages must be idempotent after partial writes; full-battery progress and cumulative campaign cost must be visible; per-slice certification must not accidentally expand into repeated wave-end audit; timing contracts must distinguish action settlement, authoritative read and Realtime convergence; a build must carry a machine-verifiable target identity for its baked `NEXT_PUBLIC_*` values; and Windows-to-WSL service failures and address changes must be classified before they can masquerade as product instability. These are test-architecture changes, not a weakening of coverage. They are recorded as enforcement candidates in [enforcement-ladder-backlog.md](../technical/enforcement-ladder-backlog.md).

The closure review also promoted the final UI lessons. Full-height web layouts use the dynamic viewport; Tailwind scans only explicit product-code roots; `TimeInput` remains custom on coarse-pointer web devices instead of falling back to a native picker; plain Server Action forms expose pending through `PendingSubmitButton`; dynamic optimistic/Realtime rows use a stable `RowActionsMenu`; correctable server validation keeps its dialog and values; and best-effort catches are permitted only for named cleanup or post-success follow-on work that cannot invalidate the outcome already reported. Their Tier 1 owners, Tier 2 checks and remaining open conversions are enumerated in the enforcement backlog rather than left only in this record.
